# Telemetry Research Report — Improving Prompts, Handoffs, and Roles

**Date:** 2026-09-10
**Scope:** full telemetry corpus 2026-06-25 → 2026-09-10; supervisor-runtime era deep-dive (49 runs, 2026-08-27 → 2026-09-10)
**Data:** all raw tables and extraction scripts in `.state/research-scratch/` (A1-cost-latency, A2-failure-atlas, A3-behavior, B1-gates, B2-first-turns, B3-verdict-findings, FT-probe-training-data). Child transcripts were archived to `.state/transcript-archive-20260910/` (1,152 JSONL sessions, 636 MB) before Claude Code's ~30-day default retention could delete them.
**Method:** read-only analysis over the central telemetry store (`%LOCALAPPDATA%/linear-agents/telemetry/telemetry.sqlite`), per-run state under `.state/supervisor/`, and archived session transcripts. Numbers below cite their source report.
**Charts:** `report/viz-data.json`, regenerated by `scripts/telemetry-viz-export.mjs` (§8).
**Revision (2026-09-10):** cost figures are deduplicated for run-scoped rows but **still 2.19× high** — a second, independent over-count was found during review (F7.1b); raw sums are 4.01× high. The first revision's "upsert on `usage_id`" fix is withdrawn as unsafe, and its recommendation to demote gemini-2.5-flash-lite is withdrawn as a misread (F3a).

## 1. Executive summary

Ranked by measured impact, not by what is most fun to fix:

1. **Failures are infrastructure-first, not prompt-first.** 22 of 38 bad turns in the supervisor era are provider-side failures (API 402 out-of-credits ×9, synthetic stream errors ×8, DNS ×5), plus background-task kills ×5 and followups that never started (pid:null) ×4. Three previously anecdotal failure modes (402, background-kill, no-system-init) are all confirmed at scale. *(A2)*
2. **The frontman is the cost center.** The supervisor (frontman) consumed $1,339 of the $3,081 deduplicated corpus (43.5%) — 2.5× all children combined ($543). A single line item: 5 turns on claude-opus-5 = $805 (26% of the entire corpus). The weekly run rate jumped from $12–238/wk (pre-supervisor) to $511–721/wk (supervisor era). *(A1)*
3. **Model routing, not prompting, drives waste.** orch-ollama sessions run at 0% cache-hit (314.7M input tokens re-billed across 4,043 turns); openrouter-minimax 61.3% cache, while opus-5 hits 97.3%. The worst behavior patterns follow the model, not the CLAUDE.md. The one apparent exception — gemini-2.5-flash-lite at 91.3% repeats — turned out **not** to be a routing fault: see F3a. *(A3, A1)*
4. **Review rounds leak.** 54% of consecutive dev↔review round-pairs re-present the same error class as the previous round. The largest single findings class is style nits (18%) — a linter's job, not a reviewer's. *(B3)*
5. **Kickoff volume is worthless; carried state is everything.** Correlation between kickoff length and first-turn context re-derivation is zero (Spearman −0.01). What removes work is a *pinned-state* section (tree, branch, base revision, issue ACs verbatim) — estimated ~30% of first-turn context calls are pure re-derivation of state the runtime already had. *(B2)*
6. **Gates are cheap by design, expensive at the tail.** 80% of gates are cleanup-approvals with ~40 s median answer time. But total human-waiting across all runs is 175.5 h; on 4 runs gate-waiting exceeded run duration (max 103% — 31.2 h waiting on a 30.2 h run); and 31% of actual question-gates were already answered by documentation — pure prompt-visibility failures. *(A2, B1)*
7. **Telemetry over-counts by ~4×, through two independent mechanisms.** Summing raw `usage_facts` across the fleet inflates ~84% (runs sharing a transcript each hold a copy — by design since ADR-0008, *not* an ingest bug), and **on top of that** one assistant message is written as ~2.57 transcript lines that each repeat the same `usage` block, inflating a further 2.19×. They multiply: **4.01×**. The corpus is therefore ~**$1,400**, not the $3,081 this report's first revision stated. Separately, `costUsdReported` from the stream is 61.6× too high for glm-5.3-flash (415× for GLM-5.2-FP8, which is also entirely unpriced — 2,732 rows at $0, making budget enforcement blind on it). *(A1, F7)*

Fine-tuning verdict: a small open-weights model is trainable **today** on verdict parsing (87 verified input→label pairs) and handoff compression (86 pairs + a 1,143-session self-supervised pool); gate pre-screening is not yet trainable (21 real labels, zero negative class). Design in §5.

## 3. Findings

### F1 — Failures are infrastructure-first *(A2)*

46 runs analyzed (3 test-fixture dirs + 1 triage-only dir skipped): **382 turns across 186 children, 90.1% exit-0.** Median turn 12–18 min across squads; p90 for dev 66.6 min.

The 38 bad turns classify as:

| Cause | n | Note |
|---|---|---|
| API 402 — provider credits exhausted | 9 | ends turn prematurely; needs balance alerting, not retry |
| Synthetic stream errors (400 "failed to extract prompt", "stream closed before completion", upstream idle timeout) | 8 | retryable at turn boundary |
| Network/DNS (ENOTFOUND) | 5 | retryable |
| Background-task kill ("Background tasks still running after 600s; terminating") | 5 | child left processes running |
| Followup never started (pid:null) | 4 | turn-start race, recorded as crashed |
| Stopped mid-turn | 3 | |
| Still open / weird endings (success report, exit 129/1) | 4 | |

Run outcomes: 23 DONE, 8 partial-no-test, 9 interrupted, 6 live at snapshot. Median run wall-clock 6.3 h, p90 30.9 h, max 40.9 h.

**So what:** the highest-leverage reliability work is a turn-boundary retry policy for transient classes (stream/network) + credit-balance alerting for 402 + a harness/prompt rule against lingering background processes — none of it is prompt prose.

### F3 — Model routing drives waste *(A3, A1)*

- 70,282 tool calls corpus-wide; 4.8% byte-identical repeats; 2.9% errors — healthy in aggregate.
- **orch-ollama: 0.0% cache-hit** on all 12 sessions, 4,043 turns, 314.7M input tokens re-billed every turn. Local Ollama has no prompt caching through this path; this workload is structurally wasteful.
- **gemini-3.8-flash: 45.7% exact repeats** across 3,314 calls in many runs — a real, live routing signal (3 subagent roles moved onto it on 2026-09-04).
- **gemini-2.5-flash-lite: 91.3% repeats — but see F3a before acting on it.** 588 of its 589 tool calls come from a single run.
- Outlier runs: review-ec58 (81.8% repeats, 44.4% errors of 658 calls), dev-e7b0 (57.1%), dev-aba1 (32.6%).
- Subagent delegation is 12.2% of cost vs the playbook's ≥40% floor — policy and practice have drifted apart.
- Cache-hit by squad: supervisor 90.6%, plan 83.0%, dev 81.6%, test 80.5%, review 79.4%, cadence 75.7%.

**So what:** decide consciously whether the ollama path keeps running uncached; revisit (or enforce) the delegation floor; watch gemini-3.8-flash, whose repeat rate is both high and spread across real runs.

### F3a — Correction: gemini-2.5-flash-lite is the permission classifier, not a squad model

The first revision of this report recommended demoting `google/gemini-2.5-flash-lite` on the strength of its 91.3% repeat rate. **That recommendation is withdrawn.** Three checks, in order:

1. **The repeats are one incident, not a pattern.** 588 of the model's 589 tool calls belong to a single run (`review-ec58`, 2026-09-01) — one `general-purpose` subagent that looped. Fleet-wide it accounts for 600 turns across 3 runs; the other two contribute 5 turns and 1 tool call.
2. **On that date the model was not even reachable through the `sonnet` tier** — `config/models.json` pointed `sonnet` at `anthropic/claude-sonnet-4.6` until 2026-09-04 (commit `17fd6ba`). The 2026-09-01 usage came from a benchmark harness, not from routing.
3. **The tier assignment it now holds was chosen by measurement.** `17fd6ba` benchmarked nine candidates on a realistic ~40k-token classifier prompt over the Anthropic protocol, scoring both verdicts: flash-lite 6/6, median 5.2 s, 0 broken replies, against `cacheRead` at $0.01/M vs sonnet's $0.30/M. The two cheaper picks before it broke the session (qwen3.8-flash rate-limited; glm-5.3-flash correct but 11.6 s median with mandatory reasoning).

**The classifier does not appear in this telemetry at all** — Claude Code does not write its permission calls to the session transcript, which is why the model shows up only when something *else* routes to it.

**What survives as a real question:** the `sonnet` tier has **two** consumers, and only one was measured. Besides the classifier, Claude Code's built-in subagents (`general-purpose`, `Explore`) request "sonnet" and therefore inherit the classifier's model. Observed since the switch: `Explore` 1 turn (09-05), `general-purpose` 4 turns (09-10) — negligible today, but a model picked for terse allow/deny verdicts is not obviously the right one for an exploration subagent. See R5a.

**Method note for future analyses:** a per-model rate is only a routing signal when its calls span multiple runs. Any model whose sample concentrates in one run should be reported as an incident, with the run named.

### F4 — Gates: cheap by design, expensive at the tail *(B1, A2)*

201 gates across 39 runs: **cleanup-approval 160 (80%, median ~40 s answer)**, question 26, plan.gate1 6, plan.gate2 5, push-approval 4. Question-gates by squad: dev 14, plan 7, test 3, review 2.

- Human latency: median 1.2 min, p90 49.7 min, max 67.6 h. **Total human-waiting: 175.5 h** (only 62.6 h inside run windows — cleanups are usually approved long after the run ended).
- Gate-waiting share of run wall-clock: median 0%, p90 15%, **max 103%** (run 7fdd: 31.2 h waiting vs 30.2 h run). 4 runs exceeded 30%.
- 24 gates remain pending (18 stale cleanups aged 44–219 h in abandoned runs; 1 push-approval; 5 questions, incl. 2 deliberately voided FOC-208 decision pairs).

Taxonomy of the 26 question-gates (8 themes):

- **31% (8/26) were already answered by documentation** → direct prompt backlog: deny-list collisions (4 — children asking to run block-listed commands), known-environment quirks living only in the supervisor's memory (2, incl. the 39.2 h outlier), Linear label retry (1), spec-review loop routing (1).
- **46% (12/26) were by-design human decisions** (experiment authorizations — the FOC-226 chain — and FOC-208 product decisions) that genuinely added human-only information (e.g. an explicit pivot-veto).
- **23% (6/26) genuine unknowns** (wrong-repo spawn failures since fixed at tool level; real mid-flight design decisions).
- **52% of answers were effectively "proceed"** (picking the offered option) — pre-stating a default in the kickoff would have removed the blocking need for a live answer in most of those.
- The `facts` field is empty in 21/26 question-gates; only FOC-208 structured its options (+ `working_default`). Structured options would make gates machine-analyzable and FT-ready.

**Case study (FOC-226):** the most expensive task in the corpus ($255.95, 35× median) is also the most gate-heavy pattern (7 experiment-authorization gates) and plausibly the 103%-gate-share run (7fdd, 11 gates) — expensive in *both* money and human attention. (Cost and gate-run linkage is plausible but not verified as the same run — flagged, not asserted.)

**So what:** add defaults to kickoffs; emit dependent decision-gates sequentially (FOC-208 emitted 2, voided, re-emitted); close stale cleanups; move known-quirk answers into squad-visible docs.

### F6 — Kickoff volume is worthless; carried state is everything *(B2)*

183/186 supervisor-era child sessions matched to transcripts (98%).

| Squad | median ctx-call share (first 15 calls) | first productive call at | sessions with no productive call in turn 1 |
|---|---|---|---|
| dev (n=56) | 33% | #5 | 23% |
| review (n=64) | 27% (37% counting `git diff`) | #5 | 30% |
| test (n=44) | 27% | #7 | 11% |
| plan (n=19) | **50%** | #6.5 | 47% — worst on every axis |

- **Kickoff length has zero effect** on re-derivation: Spearman −0.01; median 33% context-calls in *all four* length quartiles (1.1k–10.5k chars); explicit ACs: 33% vs 32%.
- Where the waste comes from: 37% of sessions re-derive git state (status/log/checkout) although spawn pinned branch/base-revision in the registry; 22% re-query Linear (FOC-264 dev: 8 of 13 calls); 17% of reads target files the kickoff itself named.
- 5/26 question-gates (19%) were direct kickoff-visibility failures (2× wrong repo/worktree, 1× kickoff named a file missing from the child tree, 1× run structure without dev tree, 1× known label-group conflict not passed on).
- **Delegation pathology:** main sessions are clean (1/183 with a >10× file re-read), but **17 subagent transcripts re-read one file >10×** (max **703×**), across 9 worktrees; the ×115 outlier (`companynewspanel.tsx`) is a subagent of the foc-99 review session. Invisible in main-session metrics.

**So what:** (1) a pinned-state section in the kickoff (tree, branch, base rev, clean-at-spawn + dirty list, issue title/AC/labels verbatim) removes ~30% of first-turn context calls; (2) spawn-time verification that kickoff-named files exist in the child tree; (3) delegation prompts should inline content/line-ranges instead of paths, and PLAN kickoffs should excerpt source material instead of mapping it.

### F7 — Telemetry trust bugs *(A1, A3, A2)*

1. **Two independent over-counts that multiply to 4.01×.** The first revision reported one ("duplicate ingest, ~84%, fix: upsert on `usage_id`"). The effect size was right; the diagnosis and the fix were not.

   **(a) Run-scoped rows — 1.83×, and by design.** `usage_facts` holds 161,221 rows for 142,841 unique `usage_id`s, and 9,722 ids appear under more than one `run_id`. That is **ADR-0008 working as specified**: a transcript file is not a run boundary, so each run sharing a file keeps its own copy. The decisive check — duplicates of the *actual* key `(run_id, usage_id)` — returns **zero**. There is no re-ingest bug to fix.

   > **Do not upsert on `usage_id`.** That was the pre-v5 key, and it is exactly the JOI-259 bug ADR-0008 removed: with a single-column key, every run after the first to share a transcript loses all its usage and shows $0. The correct handling is at *read* time, and already exists — `canonical_usage` (`scripts/telemetry-canonical.mjs`, on main since 2026-09-07) picks one claimant per physical call using the run's time window, and exposes `attribution` (`in_window` / `after_end` / `before_start`) plus `claim_count` so the confidence is visible rather than assumed. Workstream A3 used these views; A1 did not, which is where the "duplicate ingest" reading came from.

   **(b) Multi-line messages — a further 2.19×, and a real bug.** One assistant message is written to the transcript as several lines — separate lines for `thinking`, `text` and `tool_use` — and **each line repeats the same `usage` object**. `telemetry-ingest.mjs:71` turns every line into its own `usage.recorded`, keyed by byte offset; `message.id` is never read. Measured across `agents/` plus the 2026-09-10 archive:

   | | naive | per message | factor |
   |---|---:|---:|---:|
   | assistant lines / messages | 207,114 | 80,520 | 2.57× |
   | input tokens | 3.10 bn | 1.35 bn | 2.30× |
   | output tokens | 205.4 M | 74.6 M | 2.75× |
   | cache read | 10.11 bn | 4.71 bn | 2.15× |
   | **total** | **13.51 bn** | **6.17 bn** | **2.19×** |

   `canonical_usage` does **not** remove this one — the lines have different byte offsets, so they are distinct "physical calls" to it. Correct per-message usage is the **maximum** across a message's lines, not the sum: the duplicate lines carry either an identical copy or zeros (368 of 547 multi-line messages sampled were identical-copy, 179 mixed with zeros), so summing double-counts and taking the first line often reads a zero.

   **Combined: 1.83 × 2.19 = 4.01×.** Fixes: R7a (read through the views) and R7b (dedup at ingest).
2. **`costUsdReported` is untrustworthy for z-ai models:** glm-5.3-flash median 61.6× too high (confirms and extends the earlier ~58× note), glm-5.3 6–7×, GLM-5.2-FP8 415×. gpt-6-astra is accurate (0.98×). Keep pricing everything through `model_prices`.
3. **Unpriced models:** GLM-5.2-FP8 — 2,732 rows at $0, never priced; budget enforcement is blind on it. Plus early-haiku price sets, fable-5, `<synthetic>`.
4. **Fingerprint `failingTests` is empty in 86/89 verdicts** — the runtime's near-repeat detection condition (CLAUDE.md) is practically uncheckable. Enforce population at verdict-record time.
5. **Tool canon gap was a stale backfill, not a mapping gap — now closed.** 13,948 rows (19.8%) carried `tool_name_canon = NULL`. The map was not at fault: it resolved 54 of the 60 distinct names, and the NULL rows all predate 2026-09-07 16:55, when normalisation reached main (PR #23). The remaining 6 names were new arrivals — chiefly `mcp__claude_ai_Linear__*`, after the Linear MCP server was renamed from its opaque hash, plus `default_api:Bash` and `SendFeedback`. Added to `config/tool-norm.json`; `telemetry-normalize-tools.mjs --canon-only` then filled all 13,948 rows. **Coverage is now 100%** (60/60 names, 0 rows bucketed to `other_*`).

   The class of failure is worth naming: normalisation runs at ingest, so any row written while the fix was not deployed stays NULL forever unless someone re-runs the backfill. That is a monitoring gap, not a mapping gap — see R12.

6. `cost-per-task.mjs` crashes on null costUSD; `data_quality_issues`: transcript_missing 379 (176 resolved), pricing_missing 32.

## 5. Fine-tuning design (small open-weights model, local GPU)

Target confirmed with Mateusz: open-weights, trained locally. Function selection was left to the data — the census verdict:

### 5.1 Candidate functions, measured *(FT-probe)*

| Function | Real pairs today | Label quality | Production impact | Trainable now? |
|---|---|---|---|---|
| **Verdict parser** (review final text → structured findings/AC JSON) | **87 verified** (87/89 tee joins proven, ~315 KB inputs; 311 labeled findings; acMapping 72/89) | best in corpus — structure already exists | removes the fragile prose→verdict step; supports H3 | **yes** |
| **Handoff compressor** (child session → dense pinned-state handoff) | **86 pairs** (46 dev→review, 42 review→test; kickoffs found in canonical sessions 88/88, not in tees 30/123) + **1,143 sessions self-supervised pool** | good (kickoffs are real supervisor output) | **biggest cost lever** — attacks the 43.5% frontman share (F2) | **yes** (2-phase) |
| **Gate pre-screener** (question → needs-human / answerable-from-docs / type) | **21 real labels** (26 question-gates, 21 answered) | negative class does not exist — every recorded gate was by definition an escalation | would cut gate latency tail (F4) | **not yet** — needs synthetic negatives mined from docs/tees |
| Outcome predictor (features → pass/fail) | 47 tasks | tabular, not generative | triage aid | classic ML, not LLM FT |

### 5.2 Proposed design: multi-task instruction-tuned 1–3B model

- **Base:** Qwen2.5-1.5B-Instruct (or Qwen2.5-3B) — strong instruction-following at small size, English+Polish mixed data tolerable (corpus is ~30% PL in gates).
- **Method:** QLoRA. VRAM tiers: 1.5B ≈ 8–12 GB, 3B ≈ 12–16 GB (fits a consumer GPU; 7B ≈ 24 GB only if quality demands).
- **Tasks (single adapter, task-prefixed instructions):**
  1. `verdict-parse`: input = reviewer's final assistant text (+ diff stats), output = findings[] / acMapping JSON. Train on 87 pairs; extend with the 71 legacy review .md via self-supervised round-tripping (predict → validate schema → diff against recorded verdict); augmentation: schema-validation filters, not free generation.
  2. `handoff-compress`: input = child session summary artifacts (final STATUS, verdict, changed-files list), output = pinned-state handoff section (H1 format). Train on 86 pairs; phase-0 self-supervised pretraining on the 1,143-session archive (session → outline), then pair-supervise on the real kickoffs.
  3. `gate-triage` (deferred): only after synthetic negative mining (docs-question pairs generated and verified) — with 21 positives and zero negatives this is untrainable today. Interim alternative: rule-based lookup against the P5 quirks runbook — most "already-answered" gates are lookup hits, not classification problems.
- **Deployment seam:** the frontman drafts handoffs/verdicts with the small model and **reviews + approves before use** (same contract as gates — the human/supervisor stays in the loop).

### 5.3 Evaluation

- **Verdict parser:** (a) JSON schema validity 100%; (b) reconstruction — parsed output vs recorded verdict on held-out pairs (field-level F1: severity, class, evidence); (c) round-trip on legacy corpus with schema-gated acceptance.
- **Handoff compressor:** downstream metric from B2 — on held-out dev→review pairs, does the next stage's first-turn context-call share drop vs the 27–33% baseline? (B2's extractor is reusable as the eval harness.)
- **Gate triage:** F1 vs human answers, negatives validated against docs; measure as "gates the screener would have answered correctly" (target: the 8 documented-answer cases from F4).

### 5.4 Effort & cost

Extraction scripts already exist (research-scratch: `b3-classify.mjs`, B2 extractors, FT census scripts). Remaining work: dataset export hygiene (~1 day), QLoRA training pipeline (1–2 days with `unsloth`/`peft` on a consumer GPU), eval harness (reuse B2; ~1 day). Marginal cost: local GPU time only. Data stays on the machine (code + prompt content in transcripts — fine for local open-weights training).

### 5.5 Sequencing

1. **Now (no FT needed):** P1–P6, H1–H8, R3–R8 — most measured friction is fixable with config, docs and tooling.
2. **FT pilot:** verdict parser (best labels, immediate H3 synergy). Success bar: schema-valid + reconstruction ≥ recorded verdict on ≥80% of held-out pairs.
3. **FT second:** handoff compressor (biggest cost lever; depends on H1 format being adopted first — it defines the output schema).
4. **Gate triager:** revisit after 50+ real question-gates accumulate (or after structured `facts` (H5) makes labeling free).

## 8. Visualisation data

Every chart drawn from this report reads one file:

node scripts/telemetry-canonical.mjs --ensure     # views must exist first

The payload is keyed by finding, so a visualisation can be built section by section without re-reading the prose:

| Key | Series | Behind |
|---|---|---|
| `corpus` | window, runs, turns, tool calls | header |
| `F1_failures.taxonomy` | failure cause × count | F1 |
| `F2_cost` | `bySquad`, `byModel`, `byWeek`, `leadVsSubagent`, `byRole`, `budgetShares` (measured vs `graph.json` hint, with pp delta) | F2 |

| `F4_gates` | `byKind`, `bySquad`, latency, pending | F4 |
| `F5_review` | finding classes, by round, by severity, verdict outcomes | F5 |
| `F6_firstTurns` | per-squad context share, length quartiles, Spearman, AC impact | F6 |
| `F7_dataQuality` | both inflation factors + combined, canon coverage, unpriced models, attribution mix | F7 |

Three properties are deliberate. **Provenance:** `sources` records whether telemetry, research scratch and `graph.json` were all readable; scratch-derived series degrade to `null` rather than to zero when `.state/research-scratch/` is absent. **Unpriced is never folded into cost** — every cost series carries its own `unpriced` count, so a chart can show "unknown" instead of implying $0. **Both inflation factors ship together** with their product, so no chart can quote a dollar figure without the correction being one field away.

Cost series come from `canonical_usage`, so the run-scoped over-count is already gone; the message-line factor is reported, not applied, until R7b decides how history is rewritten.
