# FOC-802 — isolate child agents from the Supervisor inside the container (own uid)

Owner: delivery owner (orchestrator), 2026-10-16. Branch `foc-802-child-isolation`, cut from `main` at #71. Parent FOC-768 (M8). FOC-783 review: children spawned from `fenix-supervisor` run as the same user (`node`) as the Supervisor, so a child can edit the Supervisor's settings, records and gates on `/data`, read `/data/run/host.token` and reach the Supervisor's tmux socket. The deny lists are "not a sandbox" (ADR-0009 accepted risk).

## Facts (recon 2026-10-16)

- Image `node:22-bookworm-slim`, `USER node` (uid remapped to `FENIX_UID` at build, FOC-803), apt: git gh tmux passwd python3 …; no sudo/su-exec/gosu. The entrypoint never runs as root; every case runs as `node`. compose: no `user:`, no caps; `/data` is a named volume shared by `fenix-api` and `fenix-supervisor`; compose.yaml:74-75 states the single-user assumption.
- Spawn chain: `supervisor-spawn.mjs` (as node) creates the worktree, the launch config dir (`<runDir>/launch/<child>/turn-<n>`, bounded squad copy, no auth), `child-settings-<id>.json`, the registry entry, then spawns `supervisor-watch.mjs` detached; the WATCHER spawns `claude` and is the only writer of the tee and the registry patches. Children's own CLIs write gate answers (`gates/<id>.json`), verdicts (`verdicts/`), `edits.jsonl`, and the runtime hook writes the telemetry SQLite directly (`runtime-events.mjs:358-396`).
- Supervisor-only files: `/data/agents/supervisor` (settings, CLAUDE.md, transcripts), `/data/run/host.token` (0600, written by `supervisor-host.mjs`, read only by the api container over HTTP), `/data/state/supervisor/<run>/{children.json,triage.json,holds.json,budget.json,…}`, tmux sockets under `/tmp/tmux-<uid>/` (uid-scoped by tmux).
- Git: a child's worktree lives under `/data/workspaces/la-wt/<branch>`; its gitdir and object store live in the main clone under `/data/workspaces/<repo>/.git`, so commits need write access there.
- Docker lane (`docker/test-in-container.sh`) runs as one uid; no two-uid harness exists.

## Design — drop privileges exactly where `claude` starts

1. **Users and groups in the image** (`Dockerfile`): group `fenix` (gid `FENIX_GID`), user `fenix-child` (uid `FENIX_CHILD_UID`, default `FENIX_UID + 1000`, home `/home/fenix-child`, shell nologin, member of `fenix`); `node` joins `fenix`. apt adds `sudo`; `setpriv` comes from util-linux (verify it is present, else add). A root-owned helper `/usr/local/sbin/fenix-spawn-as-child` (0755 root:root, installed AFTER the `chown -R /opt/fenix` step) and `/etc/sudoers.d/fenix-child`: `node ALL=(root) NOPASSWD: /usr/local/sbin/fenix-spawn-as-child` — the only privileged path in the image; `Defaults!… env_keep` lists exactly the env the child needs (provider vars, LA_*, CLAUDE_CONFIG_DIR, HOME override, PATH) or the helper rebuilds the env from a JSON file written by the watcher (0640 node:fenix) — pick the file: no sudo env policy to maintain.
2. **The helper** (`docker/fenix-spawn-as-child.sh`, POSIX sh, runs as root for ~milliseconds): validates argv — `<env-file> <worktree> <config-dir> -- <claude argv…>`; refuses unless the worktree is under `LA_WORKTREE_HOME` and the config dir under `LA_SUPERVISOR_STATE_HOME`; `chown -R fenix-child:fenix` + `chmod -R g+rwX,g+s(dirs)` on the worktree, its gitdir (`.git` file → `gitdir:` path) and the config dir; then `exec setpriv --reuid=fenix-child --regid=fenix --init-groups --inh-caps=-all --no-new-privs env -i $(cat env-file) umask 0002 claude …` (with `HOME=/home/fenix-child`, `TMPDIR=/tmp/fenix-child-<id>`). Any validation failure exits 2 without starting anything.
3. **Watcher** (`scripts/supervisor-watch.mjs`): when `FENIX_IN_CONTAINER=1` and the helper exists and `FENIX_CHILD_ISOLATION` is not `off`, the `claude` spawn becomes `sudo -n /usr/local/sbin/fenix-spawn-as-child <env-file> <worktree> <config-dir> -- claude <args>`; the watcher writes the env file (the exact env it would have passed, minus nothing — the watcher's own env is the Supervisor's, so the child env is built explicitly by spawn today and passed through) with mode 0640 and removes it on exit; everything else (tee, registry patches, turn records) stays as node. Outside the container (Windows/native) nothing changes. A `--print-isolation` or status field records `isolated: true/false` on the turn record so `supervisor-status` shows it.
4. **Shared-write surface for children** (entrypoint, as node, owner of `/data`): `/data/state/supervisor/<run>/{gates,verdicts,children,launch}` and `edits.jsonl`, `/data/telemetry` (the SQLite file and its `-wal`/`-shm`), `/data/workspaces` (clones' `.git` object stores) → group `fenix`, setgid dirs, `g+rwX`; `umask 0002` for the Supervisor's own processes so new files stay group-writable; `/data/run` → 0700; `/data/agents/supervisor` → 0700; the registry, triage, holds, budget, waker stay 0644 node-owned (readable, not writable, by children). The entrypoint applies this idempotently on every start (`fix_permissions`), FOC-803-style.
5. **Claude Code needs**: `HOME=/home/fenix-child` (created in the image, 0700 fenix-child), `CLAUDE_CONFIG_DIR` = the launch dir (now owned by fenix-child), `~/.claude.json` lives under that HOME (first-run prompts are already suppressed by the launch profile — verify with the existing `init_claude_configs` logic in the entrypoint and copy the minimal `.claude.json` for the child home at build).
6. **Tests**: unit — `supervisor-watch.test.mjs`: inside-container mode with an injectable spawn asserts the sudo helper argv, the env-file contents (0640, removed after exit), the fallback when the helper is missing (today's path + a warning), and `isolated` on the turn record. Docker lane — new `docker/test-isolation.sh`: starts a throwaway container from the built image as root, runs the permission fixer, then as `node` spawns the helper with a fake `claude` (a node script) that tries to (a) write `/data/agents/supervisor/settings.json`, (b) read `/data/run/host.token`, (c) `tmux -L fenix ls` against a socket created by node, (d) write a gate answer, a verdict and an `edits.jsonl` row through the real CLIs, (e) `git commit` in its worktree, (f) emit a runtime telemetry event; asserts a–c fail with EACCES and d–f succeed, and `id -u` of the fake claude is `fenix-child`. The script is wired into CI next to `test-in-container.sh` (separate job, needs `--privileged`? no — only the container's own root, which `docker run --user root` gives).
7. **Docs**: this plan, ADR-0009 note (the accepted risk is now closed in the container), compose.yaml comment, `docs/prd/fenix-1.0.0-release-prd.md` one line, `docs/supervisor-e2e-checklist.md` AC-10-style item for the Docker lane, `docs/QUICKSTART.md` (nothing to do for users; `FENIX_CHILD_ISOLATION=off` as the escape hatch).

## Acceptance (ticket)

1. In the Docker lane a child cannot write `agents/supervisor/settings.json`, read `host.token` or connect to the Supervisor's tmux socket — `docker/test-isolation.sh` green.
2. Gates, verdicts and edits still work end to end — the same script plus the existing acceptance stack (`scripts/settings-acceptance.mjs`) after a rebuild.
3. Native/Windows runs unchanged; full Windows suite and the Linux lane green beyond the #75 reds.

## Out of scope

A per-child sandbox (bubblewrap/firejail), isolating the api container, moving the telemetry write behind a daemon (group write keeps it), the `fenix-api` bind mount of `./fenix/secrets`.

## Risks

Split-uid breaks every single-uid assumption at once: atomic writes and lock files in the shared run dir (group write + setgid handles the common path; `*.lock` files created by a child must be removable by node — `g+w` on the dir suffices), FOC-803's uid remap at build (the child uid is derived from `FENIX_UID`), and the Docker lane's single-user harness (hence a separate root-started script).

## Residual (documented)

All children share one uid (`fenix-child`) and one group (`fenix`), so a compromised child of run A can write run B's gates, verdicts and `edits.jsonl` — cross-run forgery is possible inside the shared surface. The Supervisor's own files, token and tmux socket are protected, which is this ticket's scope. Per-run child identity (a uid per run or per child) is a follow-up.
