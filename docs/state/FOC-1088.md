## 2026-11-01 — Per-task worktree lane for managed task sessions (opt-in)

Managed task sessions ran every session in the SAME main checkout — two
concurrent sessions on one repo collided on `git checkout -b` and commits
(seen live on the FOC-789 acceptance run). With `FENIX_TASK_WORKTREES=1` on
the host, each session now works in its own worktree:

- branch `foc-<n>-task`, derived from the task only (`buildBranchName`), never
  the session id — a resumed generation reuses the same branch and worktree;
  first generation pinned at the origin default branch, fail-closed when it
  does not resolve;
- worktree claimed in the workspace-claims registry as
  `task-session:<taskKey>` and handed to the pane through `FENIX_REPO_DIR`
  (no entrypoint change);
- `stopSession` (terminal and queued paths), failed starts and the pump's
  fail-closed branch release the claim; the tree is never auto-removed —
  cleanup is the operator's, a crash leaves the claim for operator recovery.

New shared surfaces: `resolveRepoFromCandidates` and
`resolveBranchStartPoint` in `scripts/supervisor-lib.mjs` (the DEV-child repo
resolution extracted from `scripts/supervisor-spawn.mjs`, both callers share
it) and `releaseClaim` (+ `release` CLI verb) in
`scripts/workspace-claims.mjs`. `scripts/supervisor-host.mjs` stamps the
controller's `FENIX_REPO_DIR` into the pane env (per-session tmux socket makes
`-g` per-session by construction).

Verification: `scripts/lint.mjs` exit 0 (920 files); task-session-host 38/38,
workspace-claims 12/12, supervisor-host 1/1, supervisor-spawn 62/62; full
`test-all` run recorded in the run hand-off. The two-session isolation lane
test fails on base e7b8735 (no `FENIX_REPO_DIR` in controller env) and passes
here. Import-layering measurement: full static load of supervisor-lib

## 2026-11-01 — Round 2: per-session repository resolution + the settings switch (default on)

REVIEW round 2 blocked the round-1 lane on the real container deployment: the
host resolved ONE repository for the WHOLE host process from
`FENIX_REPO_DIR`/`LA_SUPERVISOR_REPO`, and the container's task-session host
has neither (`entrypoint.sh` sets `LA_SUPERVISOR_REPO=$GITHUB_ROOT` only for
the pane, and `$GITHUB_ROOT=/data/workspaces` holds many repos and is not
itself a git repo) — every start failed closed, and a host-level memo would
have handed two sessions mapped to different repositories the same root.

- **Resolution is now PER SESSION**, in order: a repository on the session
  record (forward-compatible hook), the embedder pin `deps.repo`, the
  projects.json entry whose `repoRefName(repo)` equals the task key's
  workspace half (exactly one distinct repository — ambiguous or missing
  fails closed; the `${GITHUB_ROOT}/<name>` template expands against env
  `GITHUB_ROOT`), and only when no readable project map exists the env
  candidates `FENIX_REPO_DIR`/`LA_SUPERVISOR_REPO`. Memoized per resolved
  repository; failures are never memoized. `release` runs against the
  session's OWN memoized ensure() result and drops the memo, so the next
  generation re-ensures and re-claims (this also fixes round 1's stale memo
  after a failed start, which left a released claim behind a memo hit).
- **The env opt-in became a settings key**: `taskSessions.worktrees`,
  boolean, DEFAULT TRUE (delivery owner's call — data-integrity bug, the cap
  is 1 anyway). The entry-matching with the auto-pickup owner scope is ONE
  shared helper (`projectEntriesForWorkspace`), not a copy.
- **`FENIX_TASK_WORKTREES` survives as a test/emergency override** (`0`|`1`),
  winning over the overlay both ways — an operator who set `=0` under round 1
  keeps the opt-out; documented precedence lives in `docs/task-sessions.md`.
- **Fail closed with a remedy**: when no repository resolves, `lastError`
  names both fixes copy-pasteable — `fenix repo add <repository url>
  --project <the task's Linear project>` or `fenix settings set
  taskSessions.worktrees false` + `fenix restart supervisor`.
- Restart hint verified, not changed: the `fenix` script's
  `case "$2" in taskSessions.*)` wildcard after a successful
  `fenix settings set` already covers `taskSessions.worktrees`.

Verification: task-session-host (round-1 lane tests now run on the default
path, no env flag), fenix-settings (worktrees validation + round-trip),
workspace-claims / supervisor-host / supervisor-spawn regressions,
`scripts/lint.mjs` exit 0 — counts in the run hand-off.

## 2026-11-01 — Round 3: the map matches the issue's Linear project, not the workspace name

Round 2 mis-read the task key: its workspace half is the LINEAR WORKSPACE NAME
(`workspaceNameFor` → `FENIX_WORK_WORKSPACE || "jointhubs"`), not a repository
name — `repoRefName(entry.repo)` returns `linear-agents`/`office` and can
NEVER equal `jointhubs`, so on the VM every real session failed closed with
"no entry whose repo maps to workspace 'jointhubs'". The round-2 tests passed
only because they named workspaces after the fixture repositories. The red
regression run against 301174f is kept as evidence at
`.state/foc-1088-round3/red-on-301174f.txt`.

- **Resolution order (round 3)**: record repo → `deps.repo` pin (unchanged) →
  the projects.json entries whose `linearProject` equals the issue's Linear
  project (`fetchIssueFacts`: fixture first, then the GraphQL API, null on any
  failure, never throws; the pisi workspace's call is routed with
  `LINEAR_WORKSPACE=pisi`) → only when that yields no project or no matching
  entry, the entries whose STRUCTURED `ticketPrefix` field equals the issue
  id's prefix (FOC in FOC-1080 — never the note-text fallback repoPrefixMap
  accepts) → env `FENIX_REPO_DIR`/`LA_SUPERVISOR_REPO` only when no readable
  map exists. Ambiguous (two distinct repositories for one project or prefix)
  and unmatched readable maps fail closed, naming what was tried.
- **`fetchIssueFacts` is a dep seam** (`deps.fetchIssueFacts`, default a lazy
  import of `scripts/agent-state-resolve.mjs`, same pattern as `loadLib`) —
  one call per session ensure (the workspaces memo covers it), none at
  release.
- **Auto-pickup untouched**: `projectEntriesForWorkspace` keeps its
  workspace-name rule verbatim behind `linearProjectForWorkspace` — the
  owner-scope finding is filed separately by the delivery owner.
