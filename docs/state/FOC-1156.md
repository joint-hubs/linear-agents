## Item 2 — marker `node_modules/.fenix-install-ok`

Problem: a partial `node_modules` survives a failed or timed-out install and
the next `ensure` skipped it forever as "already present".

Implementation (`scripts/supervisor-lib.mjs`):

- `installDepsAt` stamps `node_modules/.fenix-install-ok` ONLY when the
  bounded install exits 0 (`runBoundedInstall` result `code === 0`); a failed
  or timed-out run leaves the tree without the marker. A marker write that
  itself fails is swallowed by design — a missing marker is the safe
  direction (the next ensure reinstalls rather than skips).
- The skip branch now requires the marker: `node_modules` present as a real
  directory WITHOUT it is stale — it falls through to the removal branch
  (`rmSync`) and a fresh install. The removal keeps the existing
  reparse-point discipline: `isReparsePoint` (the check shared with
  `supervisor-cleanup.mjs`'s prior art) decides, and `rmSync` unlinks a
  reparse point AS A LINK, never following it; a stale real directory is
  removed recursively (`rmSync(nm, { recursive: true, force: true })`).
- The record distinguishes the shapes: `replacedObstruction` (link or stray
  file, unchanged semantics) vs the new `removedStale` (marker-less tree).

## Item 3 — `*_KILL_MS` naming convention (implemented, small)

The wait-budget scan now recognizes `*_KILL_MS` constants and exempts them by
name — a constant so named is a subprocess kill-timeout by construction, so
the next kill-timeout constant needs no allowlist edit. The default posture is
unchanged: an unlisted `*TIMEOUT_MS` above 120 s still fails (pinned by the
existing TEST-r1 test, untouched).

Red-first fallback (structural reason): the convention test cannot be made to
fail on base. On base the scan regex
`\b([A-Z_]*(?:TIMEOUT_MS|POLL_MS|WAIT_MS)[A-Z_]*)\s*=\s*([0-9][0-9_]*)` never
matched a `KILL_MS` name at all, so "unscanned" and "explicitly allowed" are
indistinguishable in the violations output — both yield `[]`. The change makes
the convention explicit and pins it: if the suffix list is later extended
without the exemption, the test fails instead of the convention silently
regressing.

## Item 4 — `killFailed` branch of `runBoundedInstall`: DECLINED

The branch fires only when the timeout's tree kill does NOT land while the
child stays alive (`close` never fires; the grace timer resolves with
`killFailed: true`). Testing it deterministically needs one of:

- an injection seam for `killTree` — there is none; `runBoundedInstall` calls
  the in-module `killTree` directly, so this is a production-shape change,
  beyond the item's "cheap seam" bar; or
- a child process that deterministically survives a forced tree kill — not
  producible from a test on this platform (win32 `taskkill /F` succeeds for
  any process the test user owns; POSIX SIGKILL to an own process group
  cannot be blocked).

Declined; the branch is unchanged. The existing orphan test pins the normal
timeout path (the tree kill lands, `close` wins the race, no `killFailed`
flag on the record).

## REVIEW round 2 fix — the `created` gate made the feature dead in production

**The finding.** Round 1 gated stale reinstall on `created`. In production that
gate never opens: a fresh worktree has no node_modules (nothing to reinstall),
and the real failure path — an install times out, the next spawn REUSES the
tree, `created:false` — is exactly the pre-fix skip-forever behavior. The
round-1 test passing `{ created: true }` by hand modeled a shape production
never produces.

**New gate (required design, implemented as stated).** Stale reinstall of a
marker-less `node_modules` is allowed when EITHER (a) the ensure `created` the
worktree, OR (b) the reused tree passes BOTH checks:

- **containment** — the resolved path is strictly inside
  `worktreeRoot(<main worktree>)` (the `la-wt/<repo>/` root). Anchored on the
  repo's MAIN worktree — the first `git worktree list --porcelain` entry, the
  same anchor claimWorkspace derives — because a caller's gitRoot can itself be
  a linked worktree (`resolveGitRoot` = `show-toplevel`). The main checkout and
  anything outside the root fail the strictly-under test. Paths are compared
  through a local `normWorktreePath` (forward slashes, no trailing slash,
  case-folded on win32) — the same normalization workspace-claims applies
  internally; that helper is private, so the normalization is repeated here.
- **ownership** — the tree's workspace claim (read via the existing
  `readWorkspaceClaims` registry that `withOwnership`/`claimWorkspace` write)
  must name THIS caller's owner id.

Where the checks live: `staleReinstallDecision({ worktree, created, gitRoot,
ownerId })` in `scripts/supervisor-lib.mjs` (next to the deps-install block),
decided ONCE per `installWorktreeDeps` call and threaded into both
`installDepsAt` locations as `{ staleReinstall }` — the two locations share one
worktree path, so the vouch cannot differ between them. `installWorktreeDeps`
now takes `{ created, gitRoot, ownerId }` (default deny: no gitRoot/ownerId, or
any refused check, keeps the old skip). The spawn call site threads
`{ created: worktree.created, gitRoot, ownerId: worktree.owner }` — the owner
string `ensureWorktree` was given, stamped back on its result. Unproven
containment (no main-worktree entry, git failure) and an unreadable claims
registry deny. The junction check and the never-follow-a-link removal are
untouched. The skip reason names the cause: containment, no claim, the foreign
owner's id, or missing vouching context.

Reachability note (recorded, not a deviation): through a managed
`ensureWorktree`, a reused path outside the root is refused earlier by
`claimWorkspace` ("refusing to claim a directory outside the workspace"), and a
foreign-claimed branch is refused by `assertClaimAvailable` — so the two
keep-cases are defense in depth for direct callers (e.g. `task-session-host`
at `:410`, which passes no options and gets the safe skip) and are tested by
driving `installWorktreeDeps` directly.
