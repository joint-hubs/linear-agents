A `claude -p` win32 turn that **ends while a background task is in flight** (CLI force-kills it during turn-end teardown) leaves the claude process alive after teardown; a turn whose bg tasks all completed exits cleanly. Consistent with, not proven by, the tee alone.

### Watcher-side risk found during recon

### Root cause — simple hypothesis REFUTED behaviorally; mechanism identified statically

The "turn ends with a bg task in flight → `claude -p` process never exits" hypothesis is **refuted on 2.1.314**: all four independent shapes exited 0 within 6–8 s of the final `result`, emitting the same teardown tail as run-3409 (`task_updated killed` → `task_notification stopped` → `background_tasks_changed tasks: []`).

Static analysis of the 2.1.314 binary (`C:\Users\mateu\.local\share\claude\versions\2.1.314`, 301 MB, bun-compiled) found the print-mode `bgWait` mechanism:
- `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS ?? 600000` — default ceiling **600 s**, exactly the ~10-min linger of run-3409;
- a wait loop (`bgWaitFirstIdle`, `runPhase="waiting_for_agents"`, `hasPendingSessionWakeup`, gate `claude_print_ceiling_stop_agents`, `announceLongWait` stderr notice): if the wait for turn end (notification/session wakeup) **never resolves**, the CLI waits out the ceiling, stops agents, exits.

Run-3409 dev-3 matches ceiling-waitout: teardown 18:35:39 → external kill 18:45:55 = **616 s ≈ 600 s ceiling + ~16 s overhead**; the CLI's own exit clock would have fired ~18:45:39 (the stall row fired exactly then). dev-3 is also the only child in run-3409 whose tee does NOT end with `task_summary` (ends at `background_tasks_changed tasks: []`) and whose 6 subagent results are all `origin.kind="task-notification"` — the wait the killed task was supposed to resolve most likely never cleared. Precise trigger (unresolved `pendingNotificationWaits` vs non-exiting MCP servers) not yet isolated — **MCP is an untested confounder** (probe sessions ran with a fresh config, no MCP; dev-3 ran 7 MCP servers + codegraph).

### Unexpected finding — orphaned grandchildren (leak)

In all 3 task-bearing probes, bg-task teardown cleared the task registry (`tasks: []`) but NOT the OS process tree: the leaf process (`sleep.exe`) survived as an orphan (killed manually after each probe). Run-3409 implication: the killed Task's own processes may survive the turn — relevant for CPU/cost drift in later turns. The FOC-1154 reap (`taskkill /T`) is tree-kill, but the watcher's normal-path exit is not.

### A CLI-side lever exists (candidate fix)

`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` is statically present in 2.1.314 (6 occurrences, default 600000). Behavioral activation not yet demonstrated (no probe entered the bgWait state). Setting it (e.g. 30000) in the child env at `supervisor-watch.mjs` spawn would cap any print-mode bg wait at 30 s — the same waitout the reap fires at, but CLI-internal. Risk: premature exits during legitimate long waits (e.g. a parked session waiting on a Supervisor resume); must be tested before adoption.

### P5 — static semantics of the print-mode `bgWait` loop (binary 2.1.314)

- **Ceiling clock**: measured from `bgWaitFirstIdle` = start of the CURRENT continuous idle period (`this.bgWaitFirstIdle ??= S` when `drain.inputClosed`; nulled to `null` on any activity/work). Any wake or new turn resets it — a Supervisor resume re-arms the clock; the watcher-side SLA anchor (`lastEventAt`) behaves equivalently.
- **Loop stays in the drain** while `De = h || R (pendingNotificationWaits) || w&&!re || Ie || Se (hasPendingSessionWakeup)`. There IS an early-return path guarded by `!this.drain.inputClosed && ... && !CLAUDE_CODE_DISABLE_QUIET_BACKGROUND_WAIT` — reachable only when stdin is NOT closed (interactive session parks to background). The watcher spawns with stdio `["ignore","pipe","pipe"]` → `inputClosed=true` → **the CLI sits in the bgWait drain until the ceiling**. That is the headless-vs-interactive asymmetry.
- `announceLongWait` notice goes to process.stderr only when stderr is a terminal; in the watcher it is a pipe → notice goes to the UI channel, invisible in the tee — consistent with dev-3's tee having no wait-notice during 10 min of silence.
- `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` means **wait indefinitely** (CLI's own notice text) — must never be set to 0 in the watcher.

### Root cause (named, evidence-backed)

**On print mode with closed stdin, when a turn ends while a background-task notification wait is pending and that wait never resolves (the CLI force-killed the task during turn-end teardown without resolving its notification wait), the CLI remains in the `bgWait` drain loop until `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` (default 600 000 ms) elapses, then stops agents and exits.** The linger is CLI-internal — our watcher code is not the cause; the FOC-1154 reap at the SLA fires at almost exactly the moment the CLI's own ceiling would have fired.

Evidence: (1) dev-3 t4 teardown→external-kill = 616 s ≈ 600 s ceiling + ~16 s overhead, with the stall row at 18:45:39.476Z = teardown 18:35:39 + 600 s; (2) static symbols (`t2s`/`NGt=600000`, `bgWaitFirstIdle`, `bgWaitCeilingExceeded`, gate `tengu_print_ceiling_stop_agents`); (3) inputClosed asymmetry explaining why headless waits while interactive would return; (4) 9 behavioral probes (P0-P4) all exiting 0.3-8.2 s after result in shapes where teardown resolved the waits. **Not behaviorally reproduced**: the exact shape that leaves `pendingNotificationWaits` unresolved (dev-3's real shape had 7 MCP servers + codegraph and real subagent processes; probes could not enter the bgWait state) — trigger named statically, timing matched numerically.

### Rejected lever

`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` in the child env: **reject**. The ceiling cannot distinguish "wait that will never resolve" from "live background task mid-turn" — lowering it makes the CLI exit under a child legitimately waiting on a background task, breaking the FOC-1154 guarantee (lingering watch test AC-1d). Default 600 s = the SLA; leave it alone.

### STOP — proposed short-reap rule (delivery owner's decision)

Per the directive (cause outside our code → stop for decision before coding):

**Short reap in `scanLinger` (`scripts/supervisor-watch.mjs:567-629`), all conditions required:**
1. Terminal signature: last parsed event is a `result`, OR a `result` followed only by bounded teardown-tail `system` events (`task_updated` / `task_notification` / `background_tasks_changed` / `task_summary`), ending in `background_tasks_changed` with `tasks: []` or `task_summary` — i.e. the background-task registry is demonstrably empty.
2. Silence ≥ `REAP_GRACE_MS` (proposal: 60 s — satisfies the AC "reaped in under 60 s"; measured from `lastEventAt`, the existing anchor).
3. No pending gate (`hasPendingGate`, existing check) and child pid alive (existing recycled-pid-safe probe).

**Why it cannot fire on a healthy child (FOC-1154 AC-1d safe):** a child legitimately waiting on a live background task has a non-empty task registry and no killed-task teardown tail — condition 1 is not met, so the rule never fires; the 600 s SLA remains the only fallback. The dev-3 shape (killed task → `tasks: []` → unresolvable wait) is exactly what condition 1 detects.

**Secondary (separate decision, same STOP):** orphaned grandchildren — bg-task teardown clears the CLI task registry but not the OS process tree (leaf `sleep.exe`/tool processes survive every probe). Proposal: use the existing tree-kill (`killTree`, `taskkill /T`) on normal-path finalize in the watcher too, not only on the linger reap.
