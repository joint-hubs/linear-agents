## 2026-11-01 — Reap the lingering child after a terminal result; suppress the false stall

The bug: `scanStall` judges silence from the tee's size and mtime alone. A
child that emits `result success` and then lingers (on win32 claude never
exits on its own after the result) looks exactly like a silent turn, so the
watcher queued a false `stall` row after the SLA — the Supervisor woke, wasted
a turn on a finished child, and the wake budget bled ~10 min per occurrence.

Domain nuance kept intact: real claude can emit MULTIPLE cumulative `result`
events within one turn (background-task wake-ups re-emit; the cost suite
already covers that shape), so the gate is "the LAST parsed event on the tee
is a `result`", never "a result was seen". Every parsed stream event refreshes
the gate; any non-result event after a result flips it off and normal stall
behaviour resumes unchanged.

Mechanism (`scripts/supervisor-watch.mjs`):

- `lastEventIsResult` / `lastEventAt` module state beside `resultCosts`,
  refreshed per parsed stream event in the stdout handler.
- `scanStall` returns early (after updating `lastTeeSize`) while the last
  parsed event is a result — no stall row is ever queued for that case.
- New `scanLinger()` on the existing 5 s scanner interval: after
  `LINGER_GRACE_MS = 10_000` (seconds, well under the 120 s wait-budget
  guard) of no further stream events following a terminal result, the watcher
  reaps the child with `killTree(child.pid, "force")` and lets the NORMAL
  path do the rest — the kill fires the child's exit/close handlers, so
  `finalizeTurn` runs unchanged (registry status, gate handling →
  `waiting_gate`, cost patch, the `exit:<childId>:<turn>` wake row) and the
  watcher exits. No new wake class; the exit row carries a
  `detail.finishedLingering` marker when the reap did it.
- Bounded like the house pattern: a `lingerFinalizeTimer`
  (TAIL_DRAIN_MS + 1500, the terminator's exact window) guarantees
  `finalizeTurn` even if neither exit nor close fires after the kill; it is
  cleared by `finalizeTurn` alongside `terminatorTimer` and deliberately NOT
  unref'd — it is the last thing keeping the watcher alive.
- `finalizeTurn`: a forced kill after a terminal result must not read as a
  crash — `status === "crashed" && lingerReaped` becomes `exited` (before the
  `waiting_gate` check, so gates keep working). The kill's non-zero exit code
  (taskkill /F artifact) is recorded verbatim beside the status.

Known out-of-scope (recorded, not fixed): `cockpit.mjs` (:367, :552) and
`supervisor-status.mjs` (:76-77, :391) compute their "stalled" display state
from tee mtime independently and may still show stalled for a lingering child
until the reap completes — display only, no wake comes out of it.
