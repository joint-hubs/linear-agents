## 2026-11-01 — Reap the lingering child after a terminal result; suppress the false stall

The bug: `scanStall` judges silence from the tee's size and mtime alone. A
child that emits `result success` and then lingers (on win32 claude never
exits on its own after the result) looks exactly like a silent turn, so the
watcher queued a false `stall` row after the SLA — the Supervisor woke, wasted
a turn on a finished child, and the wake budget bled ~10 min per occurrence.

Domain nuance kept intact: real claude can emit MULTIPLE cumulative `result`
events within one turn (background-task wake-ups re-emit; the cost suite
already covers that shape), so the gate is "the LAST parsed event on the tee
is a `result`", never "a result was seen". Every parsed stream event refreshes
the gate; any non-result event after a result flips it off and normal stall
behaviour resumes unchanged.

Mechanism (`scripts/supervisor-watch.mjs`):

- `lastEventIsResult` / `lastEventAt` module state beside `resultCosts`,
  refreshed per parsed stream event in the stdout handler.
- `scanStall` returns early (after updating `lastTeeSize`) while the last
  parsed event is a result — no stall row is ever queued for that case.
- New `scanLinger()` on the existing 5 s scanner interval: after
  `LINGER_GRACE_MS = 10_000` (seconds, well under the 120 s wait-budget
  guard) of no further stream events following a terminal result, the watcher
  reaps the child with `killTree(child.pid, "force")` and lets the NORMAL
  path do the rest — the kill fires the child's exit/close handlers, so
  `finalizeTurn` runs unchanged (registry status, gate handling →
  `waiting_gate`, cost patch, the `exit:<childId>:<turn>` wake row) and the
  watcher exits. No new wake class; the exit row carries a
  `detail.finishedLingering` marker when the reap did it.
- Bounded like the house pattern: a `lingerFinalizeTimer`
  (TAIL_DRAIN_MS + 1500, the terminator's exact window) guarantees
  `finalizeTurn` even if neither exit nor close fires after the kill; it is
  cleared by `finalizeTurn` alongside `terminatorTimer` and deliberately NOT
  unref'd — it is the last thing keeping the watcher alive.
- `finalizeTurn`: a forced kill after a terminal result must not read as a
  crash — `status === "crashed" && lingerReaped` becomes `exited` (before the
  `waiting_gate` check, so gates keep working). The kill's non-zero exit code
  (taskkill /F artifact) is recorded verbatim beside the status.

Known out-of-scope (recorded, not fixed): `cockpit.mjs` (:367, :552) and
`supervisor-status.mjs` (:76-77, :391) compute their "stalled" display state
from tee mtime independently and may still show stalled for a lingering child
until the reap completes — display only, no wake comes out of it.

## 2026-11-01 — REVIEW round 1: FAIL → fixup (reap at the SLA, honest kill failure)

Review verdict FAIL on 3ca2e91 (fingerprint 2611dcdb4baa87de). Four findings,
all addressed; no declines except a scoped part of nit (d), reasoned below.

#1 (medium, lead decision = direction b, implemented): the reap now fires at
the SAME SLA the stall would have used — `stallSilenceMs()` — not a sub-SLA
grace. While the tee's last parsed event is a `result`, no stall row is queued
(unchanged); once silence past that terminal result reaches the SLA, the
linger path reaps and finalizes normally. At the SLA exactly one of
{stall row, reap} fires. Justification: real children re-emit cumulative
`result` events mid-turn on background-task wake-ups and can then sit
tee-silent for the background task's duration (proven by
supervisor-watch-cost.test.mjs's three-cumulative-results fake and the
watcher's own FOC-760 notes) — the old 10 s grace would force-kill that
healthy child and record a fake clean `exited`, a 60x sharper threshold than
the 600 s SLA on the same tee-silence signal. No new time constant:
`STALL_AFTER_MS` is reused, the FOC-608 wait-budget guard stays clean. The
ticket's real pain (Supervisor burns a wake on a false stall) is still solved:
the row at the SLA is a clean exit, not a stall.

#2 (low): liveness before the force-kill — `scanLinger` returns early when
`child.exitCode !== null || child.signalCode !== null` ('exit' already fired,
TAIL_DRAIN_MS finalize pending) or `!child.pid`; no kill can hit a recycled
win32 pid.

#3 (low): `killTree`'s boolean is honoured — one immediate retry, and a double
failure is recorded (`result_linger_reap_failed` tee note, latched via
`lingerReapFailed`) with NO fabricated `finalizeTurn(0)`: the child's own exit
stays the finalizer. `lingerReaped` is set only on a kill that actually
landed, so the `crashed → exited` status adjustment and the exit row's
`finishedLingering` marker stay truthful.

#4 (low): `child.pid` null-guarded in the same probe.

Nits:
- (a) reset path — covered: fake `result → assistant (non-terminal) → hang`
  still produces the stall row after the SLA, and the tee carries no reap note.
- (b) gate precedence — covered: a pending gate file written mid-linger makes
  the reaped turn finalize `waiting_gate` (registry + exit row detail).
- (c) multi-result re-arm — covered: `result → assistant → result → hang`
  re-arms the gate; reap at the SLA, never a stall.
- (d) liveness-probe coverage — PARTIALLY declined with reason: the guarded
  window (child exited, finalize timer not yet fired, scanner tick inside it)
  is unreachable end-to-end because finalize is scheduled TAIL_DRAIN_MS = 2 s
  after 'exit', strictly inside the ≥ 5 s SLA; hitting it would need a
  starved event loop no fixture can produce. supervisor-watch.mjs cannot be

  observational proxy IS covered: the re-emit scenario asserts a normal
  self-exit is never reaped (no `result_linger_reap` note, exit row without
  `finishedLingering`, child's own exitCode 0 preserved).
