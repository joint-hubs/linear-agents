## 2026-11-01 — Switch attach-link to attachmentCreate; dedup-by-url moved client-side

Both the CLI (`linear-ops.mjs attach-link`) and the MCP tool
(`mcp__fenix-linear__attach_link`, a pure wrapper that spawns the CLI) converge
in `handleAttachLink`, so one fix covers both paths. The tool name, argv shape
and the CLI's first stdout line are unchanged — the config-drift pins
(`scripts/config-drift.test.mjs:299`, `agents/supervisor/settings.json:31`)
are untouched.

Mechanism:

- The mutation is now `attachmentCreate(input: AttachmentCreateInput!)` with
  `{ issueId, url, title }` (all three confirmed against the live schema —
  table below), read through `AttachmentPayload { success: Boolean!,
  attachment: Attachment! }` — the same success/attachment shape the old code
  parsed, so the `link attached (id=…)` first line is byte-identical on a
  fresh create.
- Dedup moved server-side → client-side. The removed `attachmentLinkURL`
  refused a duplicate URL on the issue implicitly; `attachmentCreate` does
  not. `handleAttachLink` now queries `issue(id){ attachments { nodes { id
  url } } }` first and, if the requested URL already exists on the issue,
  skips the create and answers an idempotent success in the exact same first
  line — `link attached (id=<existing id>)` — so the MCP envelope is
  indistinguishable from a create (mapResult trims stdout on exit 0). The
  dedup query reads the first connection page (Linear default 50); an issue
  with more than 50 existing attachments could hide a duplicate.
- Egress screening (title + URL, FOC-450), the ownership gate (FOC-848) and
  both dry-run paths are unchanged and run exactly as before.
