## 2026-11-01 — the incident, and the two halves of the fix

docs/HANDOFF.md §incident (2026-11-01): a child created a `node_modules`
JUNCTION into the main checkout; `git worktree remove --force` followed it and
emptied the main checkout's node_modules — twice in one day. Two halves:

1. **Provisioning** — the child improvised an install because spawn handed it a
   tree without node_modules. Spawn now provisions deps itself, as real
   directories, before the child exists: no reason to link one in.
2. **Removal guard** — even with provisioning, a link can appear in a worktree
   (a child can still make one). The removal now unlinks reparse points AS
   LINKS before the destructive act, so git never follows them out of the tree.

### Platform facts, probed on this machine (win32, node 22.20.0, git for Windows)

- `lstatSync(p).isSymbolicLink()` reports a junction as a symlink AND as
  not-a-directory (`isDirectory() === false`) — so `existsSync` is never a
  sufficient "real node_modules" test.
- `rmSync(junction)` removes the link only; the target's content survives.
- **`git worktree remove --force` DOES follow junctions** — root-level
  (`node_modules`) and nested (`ui/node_modules`) both emptied an outside
  target directory. The red-first AC2 test reproduced the incident verbatim on
  the unmodified base.

### Provisioning design

- `installWorktreeDeps(worktree)` — `scripts/supervisor-lib.mjs` (added right
  after `withOwnership`, ~:2140). Two locations: the worktree root and `ui/`.
- **Hook point (spawn)**: `scripts/supervisor-spawn.mjs`, directly after the
  referenced-files check and BEFORE the CodeGraph launch-readiness section —
  after every free refusal (pinned state, prompt-file, referenced files), so a
  refused spawn never pays for an install; before the index preflight, so the
  codegraph sync sees the tree's final shape. Outside `ensureWorktree`'s
  integration lock on purpose: an install under the repo-wide lock would
  serialize every concurrent spawn behind one package manager.
- **Tolerance/skip rules** (per location, `installDepsAt`): no `package.json`
  → skip (`reason: "no package.json"`); `node_modules` present AND a real
  directory by lstat → skip (`"node_modules already present"`); present but a
  reparse point (or a stray file) → unlink the link only, record
  `replacedObstruction: true` (r2: renamed from `replacedReparsePoint` — the
  branch also covers a stray FILE, and the old name overclaimed), install
  fresh.
- **Command split** follows the merge tool (`supervisor-merge.mjs`
  `installIntegrationDeps`): `npm ci` with a lockfile, `npm install` without,
  both `--no-audit --no-fund`, `shell: true`, `maxBuffer` 64 MB — the same
  bounded-subprocess precedent. **[SUPERSEDED r1]** the `maxBuffer` 64 MB
  budget is gone: r1 replaced `spawnSync` with a spawned, tree-killed run
  keeping a 1 MiB output tail (see the r1 nit-5 section below).
- **Timeout budget**: `DEPS_INSTALL_TIMEOUT_MS = 300_000` (5 min). Bounded well
  under the merge tool's 900 s verify ceiling because spawn blocks the child
  launch; comfortably above this repo's own installs, which measure in seconds.
  Known accepted trade (same one the merge tool makes): a timed-out install
  leaves a node_modules a later ensure would skip as "already present"; the
  failure is in the record, never silent.
- **Failure reporting**: NOT fail-closed, mirroring the codegraph-readiness
  contract — a child that can still work without fresh deps is worth more than
  no child at all. Loud half: `console.error("[spawn] dependency install
  FAILED — the child starts anyway; see depsInstall in the spawn result ...")`.
  Durable half: a `depsInstall` record (per-location: skipped/reason/command/
  exitCode/timedOut/error/tail) in BOTH the registry entry and the spawn's
  final JSON output, beside `codegraph`.
- **DECIDED — ui/ is unconditional-when-present, not ticket-aware**: whenever
  `ui/package.json` exists, it is installed (or skipped on the rules above),
  regardless of what the child's task names. A child whose task touches only
  the root still needs the ui tree buildable, and the skip-or-install cost is
  seconds.
- **task-session-host call site** (`scripts/task-session-host.mjs`, the
  `ensure()` inside the session-workspace factory, ~:405): the same lib
  function drops in with no extra risk, so it IS applied — after
  `ensureWorktree`, outside the lock; the record rides on the memoized ensure
  result (`depsInstall` field), and a non-ok install logs one
  `console.error("task-session-host: dependency install did not complete ...")`
  line matching the host's existing error convention. The session starts
  anyway.

### Removal guard design

- `unlinkReparsePoints(worktree)` — `scripts/supervisor-cleanup.mjs`, called
  from `performRemoval` immediately BEFORE `git worktree remove` (both paths —
  recorded grant and two-key — converge there, so one guard covers both).
- **Windows reparse detection**: the repo idiom
  `lstatSync(p).isSymbolicLink()` — probed above; it reports junctions too.
- **Scan depth — depth 3, pruned** (SUPERSEDED by REVIEW r1, issue 1 — see the
  r1 section below: the walk is now full, no cutoff, no node_modules prune):
  top-level-only would have been
  insufficient (see probe: git follows NESTED junctions, and `ui/node_modules`
  is one of the two locations this same change provisions — a root-only guard
  would be self-inconsistent). The walk descends real directories to depth 3
  (root entries, their children, grandchildren), which covers
  `packages/*/node_modules` shapes too, and prunes descent into real
  `node_modules` directories (a package manager's domain, unbounded) — a
  handful of lstat calls per directory, no deep walk. Reparse points are never
  descended into; they are removed.
- **Failure mode**: a link that cannot be unlinked refuses the whole removal
  (`failJson`) — a git remove that would follow an unremovable link IS the
  incident. As with the existing git-failure path, the archive step has
  already run at that point; it is additive and the tree is left standing.
- **Report honesty**: a fifth list, `removedLinks`, in the removal JSON
  (`path — reparse point → target, unlinked before removal: git worktree
  remove follows junctions`), beside the existing `skippedLinks`/`skippedCache`
  lists — the links die with the worktree, but the list exists for the TARGET
  that kept its content.

## 2026-11-01 — REVIEW r1 fixup (six findings)

REVIEW sent back 3 issues + 3 nits on the r0 implementation. Red-first where
the finding is a bug; each subsection records the design choice and the
evidence pointer. Ambient `LA_SUPERVISOR_CHILD` unset for every run below.

### Issue 1 — the cleanup walk never entered node_modules

The r0 walk pruned real `node_modules` directories and cut descent at depth 3,
so a junction INSIDE node_modules — where pnpm's `.pnpm` store links live — was
never visited, and `git worktree remove --force` followed it exactly as happily.
**Design chosen: full walk, no depth cutoff, no node_modules prune.** The bound
is the tree's real-directory structure, not an arbitrary number: reparse points
are removed on sight and NEVER descended through, so the walk cannot loop, and
node_modules is bounded in practice (one readdir + lstat per real directory).
It runs once per removal, behind human approval — the cheapest place to be
thorough. Unreadable directories are skipped (git surfaces its own error for
those), entries that vanish between readdir and lstat are skipped (nothing left
to remove). Red-first: `red-r1-cleanup.txt` — the new junction-inside-
node_modules test failed on ac2cafd ("the removal followed the junction inside
node_modules — the walk never visited it").

### Issue 2 — the guard unlinked git-tracked symlinks (mode 120000)

A tracked link is CONTENT, not the incident shape: unlinking it changes tracked
content the approval never showed (dirty tree → non-forced `git worktree
remove` fails), and probed on this machine, leaving it is worse — `git worktree
remove --force` follows a TRACKED junction and destroys the target. **Design
chosen: refuse loudly.** `trackedSymlinkPaths(worktree)` (one `git ls-files -s
-z`, mode 120000 entries) runs before the walk; a reparse point whose path is
tracked makes the whole removal `failJson` naming the link — resolve the link,
then re-propose. Documented fallback: if `git ls-files` itself fails, the set
is treated as empty (all untracked) so the incident class stays protected —
git's own failure surfaces a moment later on the removal. Red-first:
`red-r1-cleanup.txt` — the tracked-link test failed on ac2cafd ("the removal
must refuse, not unlink tracked content"; the unfixed walk unlinked the
junction and the removal proceeded into the tracked path).

### Issue 3 — provisioning reparse-replacement had no coverage

Two tests added to the spawn suite, driving `installWorktreeDeps` directly:

- (a) junction node_modules → detected, replaced as a link
  (`replacedObstruction: true` — r2 rename, see the r2 section), target
  intact, install runs fresh into a real directory and the fake-dep resolves.
- (b) unlink fails → `ok: false` with `could not remove the node_modules
  reparse point: ...`. Simulation, stated honestly: on win32 the rm could not
  be made to fail on the JUNCTION itself (probed and refuted: cwd-pin,
  read-only attribute, an open opendirSync handle, a bare icacls deny — a deny
  ACE placed after inherited allows is never reached; `/inheritance:r` + `/deny
  *S-1-1-0:(DE)` on a file inside the directory DOES block rmSync with EPERM,
  which is what the test uses, restoring with `/reset` + chmod in `finally`).
  POSIX uses a read-only parent directory (0o555 → EACCES), restored in
  `finally`.

Red-first status: NOT red-first-able — both tests pass on ac2cafd, because r0
already contained the `if (st)` branch these tests exercise; they close the
zero-coverage gap REVIEW named rather than reproduce a bug. Evidence: the
pre-existing `red-provisioning.txt` / `red-cleanup.txt` (r0) remain in-tree at
`.state/evidence/foc-1153/`, and the Supervisor's archived copy of both lives
at `.state/supervisor/2026-11-01T14-38-08-929-supervisor-3409/evidence-foc1153-red/`.

### Nit 4 — reparse detection now consults the dirent, not only lstat

Shared predicate `isReparsePoint(st, dirent = null)` (exported from
supervisor-lib.mjs): `st.isSymbolicLink()` OR — win32 only — the readdir
dirent says the entry is a link. WHY the second view: lstat RESOLVES a reparse
point whose tag is neither symlink nor mount point (a OneDrive cloud
placeholder reads as its target's shape), while libuv's win32 scandir marks
every `FILE_ATTRIBUTE_REPARSE_POINT` dirent a link whatever its tag. Probed
here for junctions; the placeholder-tag shape is that same marker and is not
plantable unprivileged on this machine — stated honestly, the extension rests
on libuv's tag-independent scandir behavior. Applied in BOTH places: the
cleanup walk passes each dirent it already holds, and the provisioning skip
rule does a win32-only dirent lookup of `node_modules` before deciding
skip-vs-replace (an unreadable parent leaves lstat's answer as all we have).
On POSIX dirent and lstat agree, so nothing is lost. Unit test in the cleanup
suite: junction/real-dir/real-file through both views. Red-first status:
coverage/guard hardening, not a reproducible bug on this machine — not
red-first-able, said so honestly.

### Nit 5 — the timeout now kills the whole tree, and is detected structurally

`installDepsAt` moved from `spawnSync` to an async `runBoundedInstall` on
`child_process.spawn` (still `shell: true` — npm is a .cmd on win32 and node
refuses to spawn .cmd without a shell; `windowsHide: true`). The timeout is a
timer of our own, not a regex over an error message: when it fires,
`timedOut = true` and the repo's existing `killTree(child.pid, "force")` runs —
`taskkill /PID /T /F` on win32; on POSIX the child is spawned `detached` so
killTree's process-group kill lands. spawnSync's timeout killed only the
DIRECT child (cmd.exe), orphaning the npm grandchild holding locks in the
tree. Output is accumulated to a 1 MiB tail (the record only ever uses 5
lines), `error` events are captured, `close` always follows. Budget seam
`LA_DEPS_INSTALL_TIMEOUT_MS` (ignored when unset/non-positive; production
default stays 300_000) so a test can afford a REAL timeout. Red-first:
`red-r1-spawn.txt` — the orphan test failed on ac2cafd ("the preinstall
grandchild (pid 39972) survived the install timeout — the kill stopped at the
shell"). Call sites (`supervisor-spawn.mjs`, `task-session-host.mjs`) now
`await` — the only two production consumers.

### Nit 6 — the persisted record is scrubbed at the source

The repo's existing `redact()` (the FOC-783 status-filter helper, same module)
is applied in `installDepsAt` to the error first-line and every tail line
BEFORE the record is built, so the registry entry, the spawn result JSON and
anything downstream inherits scrubbed text. Two patterns extended REDACTIONS:
a URL whose authority carries credentials (`https://user:pass@host/` → scheme
kept, `***@`) and npm's `_?authToken=...` shape. Red-first:
`red-r1-spawn.txt` — the redaction test failed on ac2cafd with the raw
credential visible in the persisted tail ("the credential leaked into the
persisted record"). Probe fact behind the test's shape: npm redacts
credentials in ITS OWN error summary, and on a successful install appends
nothing after script output — so a successful install whose preinstall's last
line carries the credential URL is the shape that actually reaches the tail.

### N1 — fake credential literal trips secretlint — FIXED

The redaction test's fixture URL (`https://child:SUPERTALSEKRET@…`) is now
assembled at runtime in `supervisor-spawn.test.mjs` (`["https://child:SUPER",
"TALSEKRET", "@…"].join("")`), so secretlint's basicauth rule never sees a
literal user:pass@ shape in the source; the assertion still runs against the
assembled string (`record.includes("TALSEKRET")` must be false). The later N3
test row assembles its fake values the same way. Evidence: full-repo
`node scripts/security-scan.mjs` → exit 0, `PASS secretlint (13.0.5) — 0
findings`; scripts-scoped row (`--root scripts`, raw walk, 472 files) → exit
0, 0 findings — before the fix the scripts row failed with
`supervisor-spawn.test.mjs:528 @secretlint/secretlint-rule-basicauth`.

### N2 — taskkill failure could hang the spawn — FIXED

`runBoundedInstall` arms a grace timer (`INSTALL_KILL_GRACE_MS` = 10 s) on
EVERY timeout, right after the tree kill is issued. In the normal case (kill
landed, or the tree was already gone — `killTree`'s `false` also covers that
benign race, which is why it is not branched on) `close` wins the race and
clears the timer. If the kill genuinely did not land, the grace timer resolves
with the timeout result (`code: null`, `timedOut`, `killFailed: true`) and
logs one `console.error` line naming the dir and pid — the install record
carries `killFailed: true` next to `exitCode: null`, so the spawn can never
hang behind an unkillable npm tree.

### N3 — redaction gaps (legacy `_auth=`, query-string tokens) — FIXED

Two patterns appended to `REDACTIONS`: `/\b(_auth)\s*[=:]\s*\S+/gi` (npm's
legacy single-credential field; ordered after the `_?authToken` rule and
unable to corrupt it — `_auth` must be followed by `=`/`:`, never the `T` of
`_authToken`) and `/([?&](?:access[_-]?token|auth|token)=)[^\s&]+/gi`
(query-string tokens, key kept: `?token=***`). New test row
"the install record redacts npm's legacy _auth and query-token shapes" drives
both through a real install's stderr tail.

### N4 — partial redaction of spawnError — FIXED

`installDepsAt` now persists `redact(run.spawnError)` — the whole error,
every line — instead of only the first line. `redact`'s patterns are all
global, so multi-line spawn errors are covered end to end.

### N5 — import order — FIXED

`isReparsePoint` moved to its alphabetical place (after `isNegative`) in
`supervisor-cleanup.mjs`'s supervisor-lib import block.

### N6 — `replacedReparsePoint` overclaims — FIXED (renamed)

Renamed to `replacedObstruction`: the branch it flags also fires for a
node_modules that is a stray FILE, and the old name said otherwise. The
failure message widened to match ("…reparse point or stray file…" — the r1
failed-unlink test's regex still matches the substring). Test assertion and
the two r1 journal mentions updated to the new name.

### N7 — tracked-link refusal mid-walk loses partial removedLinks — FIXED (pre-scan chosen)

`unlinkReparsePoints` is split in two: one traversal COLLECTS every reparse
point without touching anything, the tracked check runs over the complete
set, and only a clean scan proceeds to unlinking (flat loop over the
collected links). A refused removal now leaves the tree exactly as found —
order-independent, no reliance on readdir order, nothing to lose. The
unlink-failure refusal also gained `removedLinks` in its payload. Pinned by a
new CLI test: tracked link + untracked junction in one worktree → refusal,
and the UNTRACKED junction is still in place afterwards.

### N8 — sequential installs — FIXED

`installWorktreeDeps` runs the root and ui/ installs under `Promise.all`.
Failure isolation is unchanged: each `installDepsAt` call owns its record and
its own try/catch, so a failure lands in that location's record; a rejection
(which installDepsAt does not produce short of a programming error) would
reject the whole `Promise.all` exactly as a sequential `await` would have
thrown. All suites above were re-run green on the parallel shape, including
the orphan/timeout test.

### N9 — skip-branch coverage — FIXED

Two tests added to the spawn suite: no `package.json` → `skipped: true`,
`reason: "no package.json"`; real `node_modules` directory pre-planted →
`reason: "node_modules already present"`, no `replacedObstruction`, and a
sentinel file inside node_modules proves npm never ran over it.

### N10 — git-failure fallback untested — FIXED

`unlinkReparsePoints` is now exported, and a cleanup-suite test walks a
directory that is NOT a git repo — `git ls-files` fails exactly as the
fallback anticipates (`trackedSymlinkPaths` returns null) — asserting two
planted links come back unlinked-as-links in the return, targets intact,
never refused.

### N11 — stale r0 journal bullet — FIXED

The "maxBuffer 64 MB" line now carries a **[SUPERSEDED r1]** marker pointing
at the r1 spawn + 1 MiB tail replacement; the rename note is folded into the
same bullet list.

### N12 — merged stdout/stderr tail — FIXED

`runBoundedInstall` decodes both streams (`setEncoding("utf8")`, which
carries a UTF-8 sequence split across pipe chunks) and keeps them separate;
`installDepsAt` tails stderr first (npm's diagnosis lives there) and falls
back to stdout when a run printed nothing on stderr. Trade named honestly:
when BOTH streams have content the record's 5-line tail shows only stderr —
the error channel is what the tail exists for.

## r3 — REVIEW nit round (2026-11-01, verdict PASS, 4 nits)

### N1 — parallel installs race on a workspaces-monorepo `--repo` target — FIXED

`installWorktreeDeps` now checks the root `package.json` for a `workspaces`
key before arming the concurrent ui/ install (`rootWorkspacesCover`, a
JSON.parse of the root manifest; unreadable/absent → false, which is the
pre-r3 both-installs behavior and cannot under-provision). Under workspaces
the ui/ location still appears on the record, as `skipped: true` with reason
`root package.json declares workspaces — the root install covers ui/`, so
the report stays complete. Probe that confirmed the race is real: a root
`npm install` with `workspaces: ["ui"]` even executes ui's own preinstall
script. Test added to the spawn suite (fixture root with `workspaces`,
lockfile-less so `npm ci`'s sync check cannot reject the hand-written
manifest — the command is `npm install`): root install runs and is ok, ui
record is skipped with the workspaces reason, run ok.

### N2 — link vanishing between pre-scan and unlink ENOENT-fails the removal — FIXED (tolerant)

Chosen option (a), tolerant: in the unlink loop, an `rmSync` failure with
`code === "ENOENT"` continues the loop. Rationale: the pre-scan has already
guaranteed no tracked link is unlinked, and if an untracked link vanished in
the race there is nothing left for `git worktree remove` to follow — the
failure mode the walk exists to prevent is already gone, so aborting the
whole removal buys nothing and makes cleanup unrunnable over a benign race.
The vanished link is NOT added to `removed` (this loop did not remove it; the
report must not overclaim). Every other error stays fail-closed. No test:
the scan and the unlink run inside one synchronous call with no seam between
them, and adding an injection seam to fail-safe removal code is not worth it
for a nit.

### N3 — kill-grace/killFailed timeout branch untested — DECLINED

The branch requires the tree kill to fail while `close` never fires — the
"unkillable but not closed" window. On win32 `taskkill /T /F` reliably lands
on a live same-user child (the r1 orphan test pins exactly that: the kill
DOES land), and a child that is already dead fires `close`, clearing the
grace timer. Probed equivalents (ACL deny, another owner) need elevation or a
foreign user session; a pid-dead-but-close-pending race is not pinnable
deterministically. Honest skip: not deterministically simulable in this
suite.

### N4 — multi-line spawnError redaction untested — FIXED

A spawn-suite test pins `redact` on a three-line input with a runtime-
assembled `sk-` token on the SECOND line (r2 N1 lesson: no credential literal
in source): every line must come back innocent, the credential line must
carry `sk-***`, the innocent lines must be byte-identical, and the line shape
must survive. A real multi-line spawnError is not producible end-to-end
(node's spawn failure messages are single-line, `spawn npm ENOENT`), so the
property is pinned on `redact` itself — the exact function the record path
applies to the whole `spawnError` field.

## TEST-r1 — wait-budget guard red (2026-11-01, verdict FAIL, 1 red — fixed)

TEST-7's deterministic red: `inTurnWaitViolations`
(scripts/supervisor-wait-budget.test.mjs) statically rejects any `*TIMEOUT_MS`
literal above 120 000 ms in every supervisor-*.mjs, and the candidate
introduced `const DEPS_INSTALL_TIMEOUT_MS = 300_000`
(scripts/supervisor-lib.mjs) — the kill-timeout for the new worktree deps
install. Reproduced 3x by TEST (standalone exit 1; test-all 211/212 twice).

### The choice — documented carve-out (Option 1, TEST's recommendation)

The guard now carries a minimal NAMED allowlist, `NON_WAIT_TIMEOUTS` — a Map
of constant name → reason — with exactly one entry:

- `DEPS_INSTALL_TIMEOUT_MS` — "subprocess kill-timeout for worktree deps
  install (FOC-1153); not an in-turn wait"

The carve-out applies ONLY to the uppercase-constant scan (the third loop of
`inTurnWaitViolations`); the `--timeout-ms` / `--wait` flag scans, the
120 000 ms bound and the scan scope (agents/supervisor/** +
scripts/supervisor-*.mjs) are untouched. `scripts/supervisor-lib.mjs` itself
needed no change — the constant stays at 300 000.

### The bound — 300 000 kept, and why

The constant is a KILL-timeout on the install subprocess, not a wait the spawn
blocks on: a shorter bound risks killing a legitimate cold-cache /
slow-network `npm ci`. A failed or stuck install is already loud and
non-fatal to the spawn (r0 design), so the only cost of a long kill-timeout is
lingering npm on a genuinely hung install — bounded by the kill. The env seam
`LA_DEPS_INSTALL_TIMEOUT_MS` remains the tuning path for repos with different
needs. Not a blanket `MAX_IN_TURN_WAIT_MS` raise, not a rename to dodge the
regex — both prohibited by TEST.

### Guard integrity — the default posture is pinned

Three inline-source rows in the guard suite (no scratch fixture, so nothing to
clean up):

- the allowlisted constant (`DEPS_INSTALL_TIMEOUT_MS = 300_000`) produces no
  violation — and because the guard also scans the test file itself, the
  file-level row for supervisor-wait-budget.test.mjs now exercises the
  carve-out end-to-end on every run;
- an UNlisted constant above 120 000 still produces a violation — its name is
  assembled at runtime (`["SOME_OTHER", "TIMEOUT_MS"].join("_")`) because a
  real >120_000 literal in test source would trip the suite's own self-scan
  (found on the first draft: the fixture literal failed the file-level row);
- every allowlist entry must carry a non-empty reason, so the carve-out cannot
  quietly grow undocumented.
