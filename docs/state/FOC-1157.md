## 2026-11-01 — root cause: a zero-timeout observer racing the tick's legitimate locks

### Recon (confirmed by reading the code, not just the packet)

- The test spawns the REAL telemetry-server against a per-process mkdtemp store
  with `LA_TELEMETRY_INGEST_MS=300` (`telemetry-idle-tick.test.mjs:112-121`);
  the store path is already isolated (lines 31-32) — path isolation is NOT the
  bug.
- `storeState()` (~:99-110) observes idle state through a RAW
  `new DatabaseSync(dbPath, { readOnly: true })` — bypassing `openTelemetryDb`,
  so SQLite's default `busy_timeout=0` applies: any lock contention is an
  instant `SQLITE_BUSY`, no retry.
- Every ingest tick opens its OWN connection: `ingestTelemetry`
  (`telemetry-server.mjs:464-481`) → `replayPending` + `ingestKnownRuns`
  (`telemetry-ingest.mjs:1007-1073`) → `openTelemetryDb`
  (`telemetry-store.mjs:136-152`: busy_timeout=10000, WAL,
  wal_autocheckpoint=256, then `migrate()` on EVERY open) → `db.close()` in
  `finally` (checkpoint + wal/shm cleanup as the last connection).
- `migrate()` (`telemetry-store.mjs:847-895`) unconditionally stamps
  `INSERT OR IGNORE INTO schema_migrations` (~:891-894) on every open — a short
  WRITE transaction per tick even with nothing to ingest, plus the per-tick
  checkpoint/delete/create cycle on close. These are legitimate server locks,
  not idle writes: `data_version` does not move on them (main is green, the
  assertion passes in the common case).

  both the EXACT CI signature: `FAIL idle ticks write nothing to the store:
  database is locked`. ~6.7% flake rate locally under load.
- Stack probe (temp-dir diagnostic importing the real modules; real server at
  300 ms ticks vs a `storeState()`-identical raw readOnly reader, 3 ms
  cadence): SQLITE_BUSY thrown at `ro.prepare("PRAGMA data_version")` — the
  read transaction's lock acquisition, NOT the constructor. 1 busy within 98
  attempts.
- Isolated probes (openTelemetryDb-cadence writer vs raw readOnly reader):
  bare reader on an UNLOADED machine 0 busy / 3 736 attempts; bare reader under
  the 12-burner load 0 busy / 3 801; reader with busy_timeout=10000 under load
  ("patient" — the committed fix, piloted) 0 busy / 3 870, no other errors, no
  measurable latency cost. The windows only materialize under load/slow fs —
  matching a CI-only flake.

### The fix (test-side only, `scripts/telemetry-idle-tick.test.mjs`)

`storeState()` now sets `PRAGMA busy_timeout = 10000` on the read-only
observation connection immediately after opening it — the same budget the
store itself uses (`telemetry-store.mjs:142`).

Why this does NOT weaken the idle-write assertion (FOC-808 stays detectable):

- `dbSize`/`walSize` are `statSync`'d before any locking — unaffected.
- `data_version` moves only on real committed writes; WAITING for a lock
  neither hides nor creates a commit. If the server genuinely writes while
  idle, `data_version`/`dbSize` still move and the test still fails.
- Hard ban respected: no retry loop around the assertion; the assertion body
  and the 1500 ms settle are untouched — the CI failure was SQLITE_BUSY from
  the observer, not a settle race.
- The constructor takes no locks (SQLite defers locking to the first
  statement) and the stack probe pins the throw at `prepare`, so the pragma
  set right after the readOnly open covers the exact throw site.
