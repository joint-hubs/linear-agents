## 2026-11-02 — a verdict change or new findings is progress, not a reproduced round

### Root cause

The review-loop progress guard (FOC-163) compares only the fingerprint of the
last two verdict rounds. Two verdicts recorded against the SAME tree hash
identically regardless of what each round said:

- The fingerprint (`scripts/supervisor-lib.mjs:2962-3006`,
  `progressFingerprint`) hashes the dev child's tree diff + porcelain +
  normalized failing tests. The verdict type (`pass`/`fail`), the findings and
  the round number are NOT inputs — so round N `pass` on tree T and round N+1
  `fail` on the same tree T produce the same `combined` hash.
- `comparableProgress` (`scripts/supervisor-lib.mjs:3012-3015`) compares
  `.combined` only (`null` = UNKNOWN). One caller: the guard.
- The guard (`scripts/supervisor-followup.mjs:248-264` pre-fix) refused
  whenever `repeated === true`, so the pass→fail pair — the operator's NEW
  judgment asking for rework, the FOC-1088 shape — was refused as "round N+1
  reproduced round N", and the rework the fail asks for could never start.
- The records the guard compares (`scripts/supervisor-verdict.mjs:731-751`)
  carry `taskId, runId, childId, squad, round, verdict, findings, acMapping,
  declaredAcs, fingerprint, recordedAt` (+`linearEffects` amended later); they
  are read back oldest-first by `roundsFor`/`latestVerdict`
  (`scripts/supervisor-lib.mjs:3024-3045`) from
  `runDir(runId)/verdicts/<taskid>-round<N>.json`, so both `verdict` and
  `findings` are in scope at the decision site.

### Fix semantics

`scripts/supervisor-followup.mjs`, guard block only:

- A shared fingerprint now refuses ONLY when the later round repeats BOTH the
  verdict AND the (normalized) findings of the previous one — same tree, same
  verdict, same findings = one attempt billed twice, exactly as before.
- What opens a round: a verdict polarity change (pass↔fail — operator
  judgment arriving) OR at least one finding the previous round did not have
  (findings compared as non-empty trimmed texts; a record without findings is
  an empty set). Either one is new information.
- UNKNOWN stays allowed: `comparableProgress` returning `null` (a fingerprint
  could not be read) keeps the warn-and-allow path, untouched.
- The FOC-284 incident catcher (warning-only) is untouched.
- The `progress` record written to `registry.rounds[taskId]` keeps its shape:
  `repeated` stays the raw fingerprint comparison (`true` when the fingerprints
  match, even when the resume is allowed) — the tests assert this explicitly.

### Run-id decision

Resumed Supervisor sessions reuse the run id today — both
`supervisor-spawn.mjs:113` and `supervisor-followup.mjs:71` resolve
`args.run || process.env.LA_SUPERVISOR_RUN`, so spawn and resume address the
same run dir, and the child's `telemetryRunId` is persisted at spawn and
replayed unchanged (see `cost-reconcile.test.mjs`, fixture
'run-telemetry-resumed'). Verdict rounds therefore accumulate under one run id
across resumes, which is what makes the same-tree pass→fail pair adjacent in
`roundsFor`. Decision: no change — reuse is correct; rounds accumulating under
one run id is the guard's design assumption, documented here rather than fixed.
