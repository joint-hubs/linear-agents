## 2026-11-02 — Round 1: the owner scope resolves through the projects map's workspace field

Where the comparison happened: `scripts/task-session-host.mjs`
`projectEntriesForWorkspace` filtered the projects.json entries by
`repoRefName(entry?.repo) === workspace` and `linearProjectForWorkspace`
re-checked the same equality inside its loop (the re-check was dead — the
filter had already applied it). `repoRefName` returns the repo directory
basename (`linear-agents`); the workspace half of a task key is the Linear
workspace name (`jointhubs`) — the two can never be equal, so on every
installation without task-ownership the tick failed closed with "no owner
scope for workspace 'jointhubs' — no projects.json entry maps exactly one
Linear project to a repo of that name".

**Decision: the projects-map path, not a new `autoPickup.project` config
key.** The map entries carry their OWN `workspace` field (the Linear
workspace whose tickets the mapped repository serves — `fenix repo add`
writes it, `fenix-projects.mjs add --workspace` overrides), so the resolution
is local and synchronous — workspace → entry → `entry.linearProject`, no
GraphQL call in the pickup tick and no second knob to keep in sync with the
map. The alternative (a validated `autoPickup.project` setting) would work
but duplicates a fact the map already owns and can drift from it. Fail-closed
semantics preserved: `ownerProjectForWorkspace` (the successor of both old
functions, exported for tests) throws with an operator remedy on EVERY gap —
missing/unreadable map (names `LA_PROJECTS_FILE` + the map path), no entry
for the workspace (names the `fenix-projects.mjs add --workspace` command or
`taskSessions.autoPickup.workspace`), matching entries with no
`linearProject`, and an ambiguous map (names the two projects). The throw
lands in `pickup.lastError` through the tick's catch, as before.

**Discovery worth keeping (recon missed it):** on current main the broken
rule was DORMANT — `task-ownership.mjs` (fenix-task-ownership branch, landed)
imports cleanly at host module load, so `checkOwnership` replaced the
projects.json rule on every real install. The red harness (unfixed base) with
the real tick, a stubbed linear-query child and unrestricted ownership
enqueued ALL candidates including a foreign project's (`NEO-1`) — the
fallback nobody could reach had anyone cared to test it. To make the fallback
testable the host gained a `deps.taskOwnership` seam (undefined keeps the
module-level try import; null exercises the map rule through a real tick).
Precedence is unchanged: ownership first, map rule only when the module is
absent.

Red-first evidence (unfixed base 65e5e4e, real tick harness):

## Round 2 — REVIEW round 1 FAIL (2026-11-02, fingerprint 142e188f19838717)

Two low findings, both fixed in this round.

### F-1 — secretlint fires on the redaction test's own fixture — FIXED

`scripts/task-session-host.test.mjs` (~1277): the redaction test embedded a
literal basicauth URL (`https://<user>:<secret>@<host>/<repo>` — written
here only as a placeholder shape, so this journal stays scanner-clean), and
`@secretlint/secretlint-rule-basicauth` flagged the test file, making
`node scripts/security-scan.mjs` exit 1 every run. The URL is now assembled
at runtime (userinfo parts joined with `.join("")` — the same precedent as
`supervisor-spawn.test.mjs:527`), so secretlint never sees a literal
user:pass@ shape in the source, while the redaction assertions still run
against the assembled string (`***@github.com/owner/repo` must appear,
the password part and the query token must not). No allowlist entry added
to `docs/tools/security-scan.md`.

### F-2 — case-sensitive LINEAR_API_KEY* scrub on win32 — FIXED

`scripts/test-run.mjs` (~260): the `LINEAR_API_KEY*` suite-env scrub matched
exact-case names only, but win32 env lookup is case-insensitive —
`linear_api_key` would survive into child test envs. Both prefix scrubs now
match case-insensitively: `/^linear_api_key/i` and the same one-word change
for the pre-existing `LA_SUPERVISOR` strip (~253). Decision: LA_SUPERVISOR
case-insensitivity FIXED IN THE SAME COMMIT (it is a one-line change in the
same file); no follow-up recorded.
