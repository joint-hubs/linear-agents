### Fix (a) — word-slug runs exempt from family E (position-independent)

A candidate run (same `ENTROPY_RUN_RE` boundaries) with ≥ 3 dash-separated
segments where EVERY segment is either a word or a number is a human word slug:

- **word** = `[a-z]{2,16}`, pure lowercase letters (no digits, no underscore,
  no uppercase), ≥ 1 vowel, no run of > 4 consecutive consonants;
- **number** = exactly `[0-9]{1,4}` — a 5+ digit group is a serial, not prose;
- **no empty segment** — consecutive/trailing/leading hyphens fail the shape.

Justification (each rule is a frequency argument against token material):

- the length cap (16) + pure-letters rule bans digits outright: real token
  alphabets are alphanumeric, so a random lowercase+digit segment fails at
  >99.9% — this is what keeps `foc-12-<30-char alnum token>` blocked;
- the vowel + ≤4-consonant-run checks together reject a random PURE-lowercase
  segment at ~99.99%: no vowel at all has (21/26)^20 ≈ 1.39% probability, and
  a random 20+ char lowercase string almost certainly carries a 5-consonant
  run, while every real word passes both;
- a single-letter segment fails the word rule (fail closed); a 2-segment
  all-word run has only 2 char classes and family E never flags it anyway, so
  the ≥3-segment rule is not observable in family E output (noted, still
  implemented as specified).

Implementation follows the FOC-733/FOC-788 idiom exactly: `isWordSlugRun` +
`wordSlugSpans` alongside the two existing span producers, concatenated into
`extraSpans` in both `scanEgress` and `egressSpans`. Family E only — families
A–D still fire on anything shaped like their families.

Accepted residual (same class as FOC-733's Q2-B residual; Q2-C rejected
lookup-based checks): a passphrase spelled from short lowercase words with a
small number satisfies the profile. That is exactly the grant.

### Fix (b) — pr_create base/head screened as git refs, families A–D only

`base`/`head` are structured fields: the caller already validates the ref shape
(`checkBranch`/`BRANCH_RE`), and a valid ref (a kebab branch name, a commit
SHA, `origin/main`) is not an unprefixed secret — the entropy heuristic's
class/length counting has no meaning for the field. New exports on
egress-screen.mjs: `scanEgressGitRef(text)` (families A–D only, via the shared
`detectFamiliesAD` pipeline so the detector set cannot drift) and
`assertEgressCleanGitRef(text, label)`. `server-fenix-github.mjs` pr_create now
screens title/body with the full free-text screen and base/head with the ref
screen (`screenRefOrBlock`). Fail-closed: a `ghp_` token is made of valid ref
characters and still blocks (family A), as do `sk-` (A) and JWT (D) shapes.
BRANCH_RE was left as-is: tightened patterns would reject legitimate refs
(`origin/<branch>`, dots); no real hole found — a ref cannot carry `=` or
whitespace, so families C/B are unreachable by construction yet still armed.
