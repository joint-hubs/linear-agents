## 2026-11-01 — queued chat feedback + server-side duplicate-send guard (S44, FOC-789 acceptance day 5)

What: a chat message sent from the Cockpit while the Supervisor's turn runs showed
no usable feedback — on `fenix-accept` the same text was pasted twice and the
Supervisor answered it twice.

- **Server (`scripts/supervisor-host.mjs`)**: `sendLocked` now keeps a per-host
  map of queued-but-not-proven-delivered texts (FOC-1111 duplicate guard). A send
  whose cleaned text equals a still-queued entry is refused with
  `{ sent: false, duplicate: true, queued: false }` (HTTP 200) and is NOT pasted;
  the entry is registered when a send returns `queued`, and pruned lazily at the
  next send.
- **UI (`ui/src/cockpitModel.js`, `ui/src/components/cockpit/ChatView.jsx`)**:
  `sendFeedback`/`pendingAfterSend` classify the send response; the pending chip
  now shows `delivered` when the response carried `confirmed: true` (previously
  it kept saying "sent — not confirmed yet" even though the pane had taken the
  message — the AC1 gap). `duplicate: true` removes the pending line, restores
  the typed text into the composer and shows the warning banner "Already queued —
  it will be delivered when the current turn ends.". JSX stays thin; all
  classification lives in the pure model, unit-tested in `ui/src/_tests_cockpit.mjs`.

Dedupe design decision (delivered-confirmation, not a primary TTL):
- Scope: the state lives in the `createHost` closure — one host instance per
  session (the managed task-session hosts each build their own; the legacy host
  is the one global session), so the dedupe is per-session by construction and
  the scoped `/sessions/:sid/message` route is covered for free (verified:
  `task-session-host.mjs` builds one `createHost` per controller). Two dashboard
  tabs hit the same host and share the map.
- Key: exact cleaned text (the same normalization the paste gets). The send
  mutex serializes `sendMessage = serialized(() => sendLocked(text))`, so only
  `sendLocked` touches the map.
- Delivery proof: a hook write in state `busy` with `updatedAt` AFTER the queue
  time — a prompt was taken since, and queued inputs are consumed in order, so
  ours went with it. An `idle` or `needs-input` write is deliberately NOT proof:
  the turn we queued behind can Stop or ask for permission without the queued
  input having been submitted yet; clearing on those would re-open the
  double-delivery. Consequence: keys clear lazily at the NEXT send (or the TTL),
  not at the exact delivery instant.
- Between-sends race (first delivered, then the resend): send A queues behind
  turn T1; T1 ends and consumes A (UserPromptSubmit writes `busy`, fresh
  updatedAt > A's queue time); a second send of the same text prunes the key at
  entry and goes through — legitimate, pasted again behind whatever turn is now
  running. Tested explicitly ("delivered message frees the key").
- TTL backstop (`QUEUED_DEDUPE_TTL_MS`, 15 min): a key whose queued input was
  silently lost (an Esc-cancelled turn never fires Stop and discards the queued
  input) would otherwise block honest resends forever. Trade-off, cited: a turn
  running LONGER than 15 min with the text still queued re-allows a duplicate
  resend after the TTL — accepted because the UI warning still fires and the
  alternative (no TTL) is a permanent dead-end for a lost message.
- A fresh session start (absent → started, or `fresh: true` kill+start) clears
  the map: the pane the texts were pasted into no longer exists.

Model surface added (`ui/src/cockpitModel.js`):
- `sendFeedback(res)` → `{ kind: duplicate|delivered|queued|sent, state }` —
  server response is the source of truth; unrecognized shapes degrade to `sent`.
- `pendingAfterSend(prev, res, id)` → pending lines after the response
  (state transition; duplicate removes the line).
- `duplicateWarning(res, refusedText)` → `{ text, refused }` banner payload or
  null (`refused` is the refused text — the warning's identity, since 9a3c2d8).
- `pendingChip(state)` → the chip label (queued / delivered / sent fallback).

## 2026-11-01 — review round 2: per-write delivery evidence, capped map, honest duplicate shape

Review FAIL round 1 → this fixup amends the same branch, one commit. Per-finding:

- **F1 (issue) + F3 (question) — the delivery predicate is now per-write, not
  per-map.** Round 1 freed EVERY queued key on one busy hook write (the
  per-key check ran against the same single observed write), so with two
  different texts queued behind one turn the first submission freed both and a
  resend of the still-buffered second text re-opened the double-delivery.
  Design decision (the F3 choice, made honestly):
  - The host CANNOT observe which text a hook write consumed — the hook file
    carries `state` + `updatedAt` only, never the submitted text — so
    per-message text evidence does not exist at this layer. Hardening to
    "evidence tied to THIS text" in the strong sense is impossible without a
    new observer; we chose the strongest predicate the observable evidence
    supports and wrote the trade-off down.
  - New predicate: a hook write in state `busy` is a turn START — exactly one
    submitted input — and the TUI submits its queued inputs in the order they
    were pasted (the host pastes + Enter under the send mutex; the TUI queue
    is FIFO — Claude Code processes messages queued while a turn runs in
    order received). So ONE distinct busy write frees exactly ONE key, the
    OLDEST, and only once: `appliedBusyAt` records the last write applied and
    a re-read of the same write (the file keeps only the LAST write) never
    frees a second key. A newer busy write frees the next-oldest key — the
    FIFO progression matches the drain.
  - Trade-offs, stated: (a) it still leans on FIFO drain order — the
    mechanism is the TUI's ordered message queue fed by an ordered paste+Enter
    under the host mutex; no repo-external citation beyond the queue's
    documented in-order behavior was added, so the predicate is "honest about
    being order-based", not proven absolute. (b) Under-freeing is the safe
    direction: a busy write caused by an input this host never registered
    (human typing in the pane, input queued before this host existed) frees
    the oldest key whose text may still be buffered — a bounded residual
    double-delivery window, the price of the evidence available. (c) Between
    two sends the hook file may have advanced past MORE than one busy write;
    only the last is seen, so one key is freed where two inputs drained —
    under-freeing again, a resend waits for the next turn start or the TTL.
  - Regression test: two texts queued behind one turn; one fresh busy write
    frees only the oldest (the second text stays guarded, nothing pasted);
    a re-observed write frees nothing more; the NEXT busy write frees the
    next key.
- **F2 (issue) — the pending drop is uuid-scoped.** The drop effect matched by
  text only, so a queued line whose identical text was delivered EARLIER in
  the session was dropped on the next entries update before the new copy
  arrived. Fix lives in the model (JSX stays thin): `newPendingEntry({ id,
  text, entries })` snapshots the uuids of same-text user entries at send
  time onto the pending line; `dropDeliveredPending(pending, entries)` drops a
  line only when a same-text user entry appears whose uuid is OUTSIDE that
  snapshot — a new uuid is a new delivery, re-reads of older history (same
  uuids; the transcript is append-only and `mergeConversation` dedupes by
  uuid) never drop anything. Tests: earlier-copy-kept, assistant-line-not-a-
  delivery, new-uuid-drops, snapshot-less fallback (old text-only rule).
- **F4 (todo) — startSession gates on the body, not just the status.** A 200
  with `sent: false` (the duplicate guard refused; nothing pasted) no longer
  marks the durable initial prompt `delivered`. The prompt stays `delivering`
  (the state machine's unproven state — never resent) and the session record
  goes `waiting` with the reason, matching the fail-closed shape the
  reconcile path already uses. Test drives it through the public surface
  (re-armed durable prompt + pump) with a stale-busy hook.
- **F5 (todo) — the map is FIFO-capped.** `MAX_QUEUED_KEYS = 32`, enforced
  right after insert, oldest evicted first. Chosen over a prune timer because
  keys are created and consumed only inside the send mutex — the cap is
  enforced at the same moments and a long-lived host needs no recurring tick
  just to bound a map; worst case 32 × 8 KiB ≈ 256 KiB. Trade-off: an evicted
  key re-allows a duplicate of that text — reachable only after 32 distinct
  unconfirmed sends inside the 15-min TTL. Unit-tested behaviorally (33 unique
  sends → the oldest is sendable again, the newest still guarded).
- **F6 (nit) — the duplicate body is honest.** The refused send now answers
  `{ sent: false, duplicate: true, queued: false }` — `queued: true` on a
  REFUSED send invited consumers to read it as "in the queue". Consumers
  aligned: `startDialogModel` (ui/src/workModel.js) now recognizes
  `duplicate` explicitly and says "Already queued — it will be delivered when
  the current turn ends." instead of mislabeling it "Already sent."/"Queued";
  `sendFeedback`/`duplicateWarning` keyed on `duplicate` first, so they only
  needed their pinned wire-shape literals updated. Tests updated on both
  sides (host suite + `_tests_cockpit.mjs` + `_tests_work.mjs`).
- **F7 (nit) — the TTL boundary is explicit.** The code comment now states
  the strict `>` (a key survives exactly `QUEUED_DEDUPE_TTL_MS` and is
  dropped only after it), and a test pins both sides with a clock whose
  sleep never advances: at exactly TTL the resend is still refused, +1 ms it
  goes through.
- **F8 — no action** (mutex placement, restart clear, no logging of map
  contents, hardcoded banner literal: all confirmed good).

- **[todo] stale send-time snapshot could drop the pending chip early.** The
  composer is usable while the first transcript page is still loading or the
  2 s poll is mid-flight, so `newPendingEntry`'s uuid snapshot could miss an
  identical line delivered just BEFORE the send; when that entry merged in
  later (uuid unseen) the pending chip dropped before the queued copy was
  actually delivered. Fix chosen: the snapshot-side option, NOT the
  `!loaded` send gate — the gate cannot cover the mid-poll half (the poll is
  always up to 2 s behind), while a `sentAt` floor (client `Date.now()` at
  send, carried on the pending entry) covers both halves with one rule: the
  transcript is append-only and server-stamped, so an entry stamped at or
  before `sentAt` existed before the send and is never this send's delivery —
  only an unseen uuid stamped AFTER the send drops the line. Clock-skew
  trade-off: a client clock ahead of the server only DELAYS the drop until
  the queued copy's own entry lands (never a false early drop; never stuck) —
  same-host compose clocks make it negligible. ts-less/unparseable entries
  still count as new (defensive), and a pending entry without `sentAt` falls
  back to the round-2 uuid-only rule. Regression: the stale-merge test (send
  with an empty snapshot, a pre-send twin merging in later with ts <= sentAt
  → kept; the copy's own entry with ts > sentAt → dropped) plus the
  defensive-fallback tests in `_tests_cockpit.mjs`.
