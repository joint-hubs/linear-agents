Goal: one pool identity per run inside the container — every run's children run as the run's own
`fenix-child-<n>` (primary group `fenix-run-<n>`), so a child of run A can no longer write run B's
gates, verdicts, `edits.jsonl`, launch state, tees or worktree, nor read run B's `child.env`, while
`node` keeps every write. Design: `docs/plans/foc-878-per-run-child-identity.md` (accepted
2026-11-07). Docker lane only — native (Windows) runs keep the deny-list posture (ADR-0009).

## Interpretation note (required by the spec): fix_permissions vs the run groups

The entrypoint's `fix_permissions` walks the shared `/data` trees with `chgrp -R fenix` on every
restart. After FOC-878 a run's shared subdirs and `edits.jsonl` carry the run group
`fenix-run-<n>` — and `fenix` is a supplementary group of every pool user, so a plain recursive
`chgrp fenix` would hand the run's trees back to every child in the container, reverting the
invariant on the next restart. The walk therefore prunes `fenix-run-*` gid entries
(`find <tree> \( -gid … -o … \) -prune -o -exec chgrp -h fenix -- {} +`, the gid list built from
`/etc/group` at runtime) — a claimed run's group ownership survives a restart. The chmod walks are
unchanged (additive `g+rwX`, no group change). The same rule protects the cache subtrees:
`fix_cache_permissions` skips any cache subdir already owned by a `fenix-run-*` group.

## Resolved ambiguities (recorded for review)

1. **Slot 0 keeps the old uid, no alias user.** Uniform `fenix-child-<n>` naming only; the CI
   thin-layer assertion moved from `id -u fenix-child` to `id -u fenix-child-0` (same number
   2234 — the spec's "the thin layer remaps the whole pool" made the rename required).
2. **A slot is taken when ANY other run's identity.json names it, regardless of liveness.**
   The narrow "live children only" reading would let two alternating runs share a slot between
   turns, breaking the §2 invariant; the conservative reading (identity.json blocks, /proc is
   only the second signal) is implemented.
3. **Identity absent ⇒ assign at that spawn.** No legacy branch and no migration walk: the first
   spawn of a legacy run claims the lowest free slot and re-groups the four shared subdirs plus
   `edits.jsonl` ("nothing migrates in place" applies to file contents, not to the four subdirs
   the spec names). Pre-existing files keep group `fenix` (supplementary) until that spawn.
4. **`supervisor-spawn.mjs` does not record the identity — the watcher does.** The spawner exits
   before the first child spawn, so it cannot know the slot; the helper claims the identity at
   the watcher's spawn and `supervisor-watch.mjs` records it on the registry entry at turn end
   (`entry.identity`), beside the run-level field status reads from `identity.json`.
5. **`FENIX_CHILD_POOL` reaches the helper via the image ENV + one sudoers line**
   (`Defaults!/usr/local/sbin/fenix-spawn-as-child env_keep += "FENIX_CHILD_POOL"`) — sudo strips
   the environment, and the helper re-validates every slot against `/etc/passwd` so a spoofed
   pool buys nothing.
6. **The share helper's runas is the run's own pool user** (`CHILD_SHARE_RUNAS` default
   `fenix-child-0`, resolved per run from `identity.json`, regex-guarded) — slot 0 keeps the
   legacy child's uid, so transcripts a pre-pool run left behind are still chmodded by their
   owner; sudoers names the `%fenix-children` umbrella so one entry covers the pool.
