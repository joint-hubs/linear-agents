# FOC-1162 — orphaned grandchildren survive the normal-path finalize on win32

Follow-up to FOC-1160 ("Secondary" item B, filed as its own ticket). Append-only journal.

## 2026-11-02 — recon + RED (dev-2, run 2026-11-02T06-28-45-577-supervisor-c728)

### The bug

On win32, when a supervisor-watched child exits on its own (the NORMAL-path finalize, exit 0), anything it spawned — detached grandchildren, tool processes — survives. Nothing kills it: the child's own exit takes nothing with it, and the only stray-reaping the finalizer knows is the FOC-808 sweep (`sweepChildProcesses`), which is /proc-only and returns `skipped: "no /proc"` on win32. A leaked detached grandchild runs until it dies of old age.

FOC-1160 already observed the leak shape empirically: in all 3 task-bearing probes the bg-task teardown cleared the CLI task registry but NOT the OS process tree — leaf `sleep.exe` survived every probe. That observation became this ticket.

The fake emits `system/init`, spawns a long-lived DETACHED grandchild (`node -e "setTimeout(() => {}, 60000)"`, stdio ignore — no pipe hold, so `close` fires on the child's own exit), writes the pid to `GC_PID_FILE`, exits 0. ### Mechanism chosen

**One full-table CIM enumeration at finalize + a BFS over `ParentProcessId` links, verified against creation stamps.**

`scripts/supervisor-lib.mjs` (new section "win32 descendant reap (FOC-1162)" after `sweepChildProcesses`):

- `enumerateWin32Processes({timeoutMs})` — `Get-CimInstance Win32_Process` full table (~1 s for 522 processes on this host), one PowerShell call, output parsed by `parseWin32ProcessTable`. `CreationDate.Kind === "Local"` verified empirically in a probe, so `ToFileTimeUtc()` converts with no timezone skew; microsecond precision. FILETIME (100 ns ticks since 1601) exceeds JS safe-integer range, so the conversion to epoch ms happens INSIDE PowerShell: `([long](($_.CreationDate.ToFileTimeUtc() - 116444736000000000) / 10000))`.
- `parseWin32ProcessTable(text)` — `pid|ppid|epochMs|name` rows; any non-empty unparseable line refuses the WHOLE table (fail-closed: garbage in → no kills, never a wrong kill).
- `descendantsInProcessTable(entries, rootPid, {maxCreationMs})` — pure BFS over `ppid → children`; root never included. Two creation-stamp verification rules (see below).
- `reapChildDescendants({rootPid, exitAtMs, excludePids, ...})` — orchestration: enumerate → BFS → kill ONLY topmost verified pids with `killTree(pid, "force")` (taskkill /T /F — the /T walk covers post-exit great-grandchildren, so deep chains need no BFS completeness for the kill itself, only for finding the tops) → bounded grace poll (50 ms steps) → verification re-enumeration names survivors. Survivors use creation-stamp matching: a pid that re-enumerates with a DIFFERENT creation is a reused pid, never named a survivor. `survivors: null` means verification itself failed (unknown — never read as "all dead").

`scripts/supervisor-watch.mjs`:

- `childExitAt` recorded the instant the child's `'exit'` fires — the creation bound the reap verifies against. A process the child spawned was born before this moment; a pid-reuse stranger's child after it.
- In `finalizeTurn`, after the FOC-808 sweep block, win32-only guard `process.platform === "win32" && childExitAt !== null && (child.exitCode !== null || child.signalCode !== null)`: calls `reapChildDescendants({rootPid: child.pid, exitAtMs: childExitAt, excludePids: [process.pid]})`, records `reapedTreePids` in the turn record, and notes `child_tree_reap` / `child_tree_reap_skipped` / `child_tree_reap_survivors` / `child_tree_reap_failed` in the tee.
- Guard interplay with FOC-1154/FOC-1160: the linger last-resort finalize (child still alive) has `child.exitCode === null` → the reap does not fire there; the linger force-kill already walks the live tree via taskkill /T. The short reap (FOC-1160) kills the child itself with the same tree-kill. So the new reap only ever runs on the child's own death — exactly where the leak was.

### Descendant-check semantics (the two creation-stamp rules)

The win32 problem that needs them: a dead parent's `ParentProcessId` links stay visible in CIM, and pids get reused. Bare link-walking would both miss orphans (chain through a reused pid) and kill strangers (a new process that happens to hold the child's pid).

1. **Anchor rule** — a child of the root pid is accepted iff `creation <= exitAtMs` (the child's recorded death time). Everything the child spawned was born before the child died; a pid-reuse stranger's child was born after. The rule only binds when `maxCreationMs` is finite — without an exit bound NOTHING is accepted (fail-safe).
2. **Chain rule** — a grandchild is accepted iff `creation > parent.creation`, where the parent is a live accepted table entry. Everything born by the pid's current holder postdates the holder's own birth; a leftover child of a dead previous holder predates it. If the middle link died AND its pid was reused, the chain breaks at the reuse (safe miss — an orphan survives, but no stranger is ever killed).

Residual, accepted and documented: (a) a descendant chain whose middle link died and whose pid was reused breaks the walk — the true orphan below it survives this reap; (b) a false kill would require a stranger to reuse the anchor pid AND spawn a child within the microsecond-scale window between the child's death and `exitAt` recording. Both residual risks are strictly better than the status quo of killing nothing.

### Rejected candidates

- **Periodic while-alive snapshots** of the child's tree (enumerate every N seconds so the exit-time table is exact): heavy per-tick PowerShell spawns for every live child turn, and the exit-time enumeration with a creation bound is airtight without them. Lost.
- **Job Objects** (spawn the child in a Windows Job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`): the airtight OS-level answer, but no native module reach — `package.json` has only ajv/ws/node-pty, and a build dependency for one platform is not worth it here. Lost.
- **wmic**: removed from this Windows 11 build (`wmic` is not on PATH). Lost.
- **tasklist alone**: no `ParentProcessId` column in default output — cannot walk the tree. Lost.

### POSIX answer (analyzed; this suite runs win32, test 3 needs no POSIX guard but the mechanism is win32-only)

On POSIX the watcher does not need a new reap:
- `killTree` signals the child's own process group (`process.kill(-pid, signal)`; POSIX children spawn detached → they lead their own group), which reaches non-detaching grandchildren on every kill path.
- The NORMAL exit path is covered by the FOC-808 env-mark sweep (`sweepChildProcesses` via `LA_CHILD_MARK` riding the environment, inherited even by setsid-ed grandchildren).
- Residual gap (pre-existing, not this ticket): a grandchild that deliberately clears its own environ escapes the mark sweep. No code change on POSIX; `reapChildDescendants`'s non-win32 path returns `{entries: [], skipped: "not win32"}` and is never called there.

## 2026-11-02 — fix round 3, CI-Linux red: the fixture's grandchild survived the POSIX finalize (dev-1, run 2026-11-02T08-11-50-404-supervisor-f37b)

CI on the Fenix Linux image went red on the round-2 candidate (`7041ee0`): `supervisor-watch-grandchild-reap.test.mjs` failed with "grandchild pid N SURVIVED". The round-2 signal-0 probe exposed what the old `aliveViaCim` probe had been passing vacuously on Linux: on POSIX nothing reaped the grandchild.

### Confirmed cause — the fixture exercised a shape production never produces

On POSIX the finalize's stray-reaping is the FOC-808 env-mark sweep. `sweepMarkFor` (`scripts/supervisor-lib.mjs:3172-3183`) accepts `entry.mark` (authoritative, prefix-free) or `LA_CHILD_MARK` from the env, but only when it starts with `${runId}/${childId}/`. Production always carries the mark both ways (`supervisor-spawn.mjs:957-961,1025,1215` — same value as registry `mark` and child-env `LA_CHILD_MARK`). The round-1 fixture set NEITHER: its env came from `scrubbedEnv()` (which deletes ambient `LA_CHILD_MARK`) and its hand-written registry entry had no `mark`/`attemptId` → `{ mark: null }` → the sweep gate (`supervisor-watch.mjs:892,901`) silently skipped. The FOC-1162 descendant reap is win32-gated (`supervisor-watch.mjs:975-979`), so win32 passed and masked it.

### Fix — fixture-only (`8329482`)

`scripts/supervisor-watch-grandchild-reap.test.mjs`: const `CHILD_MARK = ${runId}/dev-1/dev-1:turn:0` (production form via `attemptIdFor`, `agent-launch-profile.mjs:74`); the registry entry carries `mark: CHILD_MARK` and the watcher env carries `LA_CHILD_MARK: CHILD_MARK` — both carriers, like production. The mark rides the spawn chain (watcher → `env: process.env` at `supervisor-watch.mjs:334` → fake claude → detached grandchild) into the grandchild's environ, which is what `sweepChildProcesses` scans on `/proc`. No platform skip; the three assertions unchanged; production code untouched. No PRODUCTION-BUG: with a correct mark the sweep owns the grandchild.
