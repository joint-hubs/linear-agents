## 2026-11-01 — needsText on hold options, end to end

### Field name + delivery contract (as implemented, server → UI)

- Hold options gain an optional boolean **`needsText`**. Absent/false = no text
  needed; old hold records on disk without the field are tolerated (fail open,
  enforce on new). `validateHoldStore` is not a strict key whitelist, so the
  flag round-trips writeHolds→readHolds unchanged — no validation was loosened.
- `scripts/agent-state-resolve.mjs` sets `needsText: true` on the
  "Provide the values" option of the working-state hold it creates.
- UI: `inboxPrimaryAction` maps a hold whose options carry a `needsText` flag
  to the new action kind **`option-text`**. A needsText option does NOT submit
  its label on click — clicking reveals a text field (reusing the existing
  `answerText` textarea pattern); submit is disabled while the text is empty;
  on submit the body is `{ runId, holdId, text: <trimmed values>, optionLabel: <o.label> }`.
  Options without `needsText` behave exactly as before (click submits the label).
- `answerHold` accepts optional `optionLabel` (non-empty string ≤ 200 chars
  when given; else `invalid-answer` refusal → HTTP 400) and stores it as an
  optional field on the answer record — absent when not given, so old records
  and CLI answers keep their exact historical shape.
- Server enforcement: `POST /api/holds/answer` refuses with **400** when no
  `optionLabel` is given and the trimmed text exactly equals a `needsText`
  option's label of that hold (the legacy bare-label payload this bug
  produced). Values without `optionLabel` are still accepted (a real, if
  label-less, answer); the existing `text` non-empty validation is unchanged.
  The pre-check reads the hold through `readHoldQuietly` (never throws); an
  unreadable store changes nothing — `answerHold` reports it with its own code.

### Hold-creation-site sweep

- `scripts/agent-state-resolve.mjs:477` — the only hold-creation site setting
  option flags directly; now sets `needsText: true` on "Provide the values".
  (`cmdHold` also builds options, but through `parseOption` — see next bullet.)
- CLI `--option <json>` → `parseOption` (`scripts/supervisor-gate.mjs`) returns
  a fixed-shape `{ label, model, costUsd, unpricedModel? }` and would silently
  DROP a `needsText` field. Documented limitation, deliberately not extended:
  no CLI-created hold currently needs text; extending parseOption is the fix
  if one ever does.
- Every other `options: [` hit in `scripts/` is a test fixture or the
  unrelated ask/dialog options shape (`{text, recommended}` / `{label}` in
  session-dialog / plan-intent) — not hold options.

## 2026-11-01 — fixup round 1 (review FAIL → fixed)

REVIEW failed the round-1 implementation with two issues; both are fixed by
MOVING the bare-label refusal into `answerHold` (review option (a)).

### Findings

- **Issue 1 — route pre-check unguarded and misordered** (`cockpit-routes.mjs`):
  the bare-label refusal read the hold with the RAW body runId BEFORE
  validation/ownership (`invalidId` never saw traversal-shaped runIds; the
  pre-check ran before `denyIfLegacyReadOnly` and `verifyRunOwnership`, making
  the endpoint a cross-session hold-existence oracle). Choice (a) taken: the
  refusal now lives in `answerHold` — the single choke point the CLI and the
  route share — where the hold is already read, validated and owned. It was
  the smallest correct move; `answerHold` already owned the hold read and the
  state checks, so nothing new had to be threaded through.
- **Issue 2 — CLI bypass**: `answer --hold --text "Provide the values"` on a
  needsText hold recorded the bare label; `applyHoldAnswers` drops lines
  without "=" and hold-dedup suppresses the re-prompt, so the original bug
  survived on the CLI path. Same fix as Issue 1: the rule fires in
  `answerHold` with the existing `invalid-answer` code and the route's 400
  message text. `answerErrorStatus` already maps `invalid-answer` → 400, so
  the Cockpit's refusal status is unchanged — verified, no mapping adjustment
  needed.
- Refusal semantics preserved exactly: refuse only when NO `optionLabel` is
  given and the trimmed text equals a needsText option's label; a real values
  answer — with or without `optionLabel` — passes. The match now scans EVERY
  needsText option (round 1 compared only the first `.find` hit).
- **Route nits collapsed** (confirmed, as review predicted): the pre-check's
  `.find`-only-first-option issue is gone (answerHold scans all options), and
  the answered-hold 400-vs-409 inconsistency is gone (answerHold's
  `already-answered` check runs first, so re-answering an answered hold gets
  409 whether or not the text looks like a bare label). One refusal, one
  order: not-found → already-answered (409) → bare-label (invalid-answer).
- **Nit**: `parseOption` (`supervisor-gate.mjs`) now carries a comment at the
  return shape documenting that a `needsText` flag on `--option` JSON is
  silently dropped — the CLI-created hold would not carry the flag.
- **Nit**: tightened the hold-creation-sweep wording in the round-1 entry —
  `cmdHold` also builds options (through `parseOption`).
