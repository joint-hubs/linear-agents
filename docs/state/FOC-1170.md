## 2026-11-02 — what changed, per item

### 1–2. `supervisor-verdict.mjs` — `--ran` and `--red-first`

- `evidenceRuns` (`scripts/supervisor-verdict.mjs:666`) parses and shape-validates both flags:
  `--ran` needs `cmd` (non-evidence-checked string), integer `exit`, non-empty `outputRef`;
  `--red-first` needs the same plus integer `baseExit`/`candidateExit`. Shape errors are refused
  for ANY verdict (details in `problems[]`, message `the evidence flags are malformed`).
  `baseExit === candidateExit` is refused by name (`red-first-not-red`, line 696).
- `checkOutputRef` (`:716`) resolves the ref (absolute as-is; relative against the REVIEWER's
  worktree first — that is the cwd the reviewer ran in — then the tool's cwd, then the run dir),
  refuses missing (`evidence-outputRef-missing`), empty — zero-byte file or empty dir
  (`evidence-outputRef-empty`) — and outside (`evidence-outputRef-outside-run`) anything not
  under `<runDir>/scratch` or `entry.worktree`. The RESOLVED ABSOLUTE path is what lands on the
  record, so the citation stays readable from any cwd later.
- The ≥1 requirement is a review-pass gate only: `verdict === "pass" && entry.squad === "review"`
  with no `--ran` → `review-pass-without-evidence-run` (`:848-864`, wired after the
  failing-test-declaration gate). A fail does not need it; a fail that CITES a `--ran` still
  gets the shape + outputRef checks (evidence that does not exist is not evidence on a fail

- Record keys `ran: [...]` / `redFirst: [...]` (`:915-917`), spread conditionally — a

## 2026-11-02 — what the AC leaves ambiguous (decisions taken)

1. **outputRef checks on a fail verdict**: the AC pins refusal only for a pass. Decision: shape
   validation applies to any record citing the flags; the existence/empty/containment check too
   — pinned by `a --ran cited on a fail still has to point at real output`. Softer than
   refusing, harder than ignoring; a fail record citing a nonexistent file is still a lie.
2. **Red-first semantics beyond equal exits**: the AC refuses only `baseExit === candidateExit`.
   A pair like `baseExit: 0, candidateExit: 1` (candidate got WORSE) is therefore accepted —
   that is a documented non-improvement claim, useful on a fail record; over-refusing would
   block it. `red-first-not-red` stays exactly the equal-exits refusal the ticket names.
3. **Delivery mode and the new flags**: `cmdRecordDelivery` does not read `--ran`/`--red-first`
   (FOC-1169's shape stays untouched; the ticket scopes the gate to "a review child"). They are
   silently ignored there today, unlike `--child`/`--ac` which are refused. Proposed follow-up:
   refuse them in delivery mode the same way, if a delivery red-first claim is ever wanted it
   should be designed in, not smuggled through.
4. **Non-review squads recording passes** (plan/test/cadence children via the same `record`):
   the gate is scoped to `entry.squad === "review"` per the ticket; other squads' pass records
   are unchanged in shape and requirement.

### Blocking — delivery mode silently accepted the evidence flags

`cmdRecordDelivery` refused `--child` and `--ac` by name and then never read `args.ran` /
`args["red-first"]` — a cited evidence flag parsed and vanished (reviewer probe P14b: `record
--delivery … --ran <valid>` → `ok=true`, `ran: null`). This was ambiguity #3 from the pre-round
section above, and the reviewer endorsed the proposed fix: refuse by name, the same pattern as
`--child`/`--ac`, NO record-shape change.

- Fix (`scripts/supervisor-verdict.mjs`, `cmdRecordDelivery` guard block): `--ran` and
  `--red-first` present in `--delivery` mode → `failJson` naming the flag
  ("--ran is not used in --delivery mode — an evidence run is a REVIEW pass requirement",
  same wording for `--red-first`).
- Pinned by two tests beside the other delivery-gate pins; "a delivery pass needs no reason and
  no AC mapping" additionally asserts `out.ran === undefined` (shape stays byte-identical
  without the flag).

### Nit folded — containment was case-sensitive on win32

`checkOutputRef`'s containment was a raw `startsWith` string compare: a citation typed with a
lowercase drive letter (`c:/users/...`) resolved fine on the case-insensitive win32 filesystem
and was then refused `evidence-outputRef-outside-run` although the file sat inside the
reviewer's worktree (reviewer probe P15). Fix: both sides of the containment compare are
case-folded when `process.platform === "win32"` — posix paths ARE case-sensitive, so the fold
must never run there. Pinned by "an outputRef whose path casing differs from the root is still
contained (win32)", which steps aside on non-win32 platforms (the scenario does not exist on a
case-sensitive filesystem).

### Journal wording correction (reviewer nit 2)

The pre-round section overstated the template pins. Corrected claim: `scripts/launch.test.mjs`
forbids the kickoff templates carrying only model names, Linear team keys and rival loop
definitions — it does NOT keep `DEFAULT_KICKOFF_TEMPLATES` equal to `config/prompts.json`, and
no test does; the sync of the FOC-1170 line between the built-in default and the editable copy
is manual. Both copies carry the line today (verified before the round-1 commit).

### Question answered — no change: red-first accepts a worsening exit pair

`--red-first` with `baseExit: 0, candidateExit: 1` (candidate got worse) is stored as-is. The
reviewer asked whether to name the direction (e.g. a derived `direction: "worse"`). Decision:
leave it. The record's job is to store the exits verbatim — the reviewer's claim, not the
tool's interpretation of it; a derived key would be the tool editorializing on a record whose
whole value is that it carries what the reviewer asserted. Any consumer (including the FOC-946
reflector) can compare two integers. AC-conformant: only equal exits are refused.
