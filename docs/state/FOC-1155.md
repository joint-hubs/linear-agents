## 2026-11-02 — `--work-run <runId>`: resolve the work child across a run split

### Root cause (with evidence)

A Supervisor launcher restart mid-task starts a NEW run. Children registered
before the restart stay in the OLD run's `children.json`; children registered
after it land in the NEW run's. `supervisor-verdict.mjs` bound
`--child` (the recording child) and `--work-child` (whose tree holds the work
under review) to ONE registry — the verdict's own run's:

- `cmdRecord` resolved everything from `runId` (from `--run` /
  `LA_SUPERVISOR_RUN`): `readRegistry(runId)` then
  `resolveWorkChild(registry, entry, taskId, args)` — pre-fix
  `scripts/supervisor-verdict.mjs:552-561, 717`.
- `resolveWorkChild` (pre-fix `scripts/supervisor-verdict.mjs:175-212`)
  searched `registry.children` only. A TEST child registered in run B recording
  the DEV child `dev-1` registered in run A was refused:
  `--work-child "dev-1" is not in the registry` — fail-closed, correct as a
  refusal, but the TEST child then could not record its PASS.
- Seen 2026-11-01 (FOC-1110): the Supervisor worked around it by hand-copying
  dev-1's entry into the new run's registry with a `crossRunImport` note —
  a second source of truth, which is exactly what we are replacing.

### Chosen semantics (operator's option (b) — explicit provenance, not import)

Option (a) (import the previous run's live task chains at start) was rejected:
it adds a second source of truth. Implemented, all five spec points:

1. **Cross-run resolution** — `--work-run <runId>` makes the work-child
   resolution search THAT run's registry. `cmdRecord` parses the flag
   (`scripts/supervisor-verdict.mjs`, `workRunId` block in `cmdRecord`), and
   `resolveWorkChild(registry, entry, taskId, args, workRunId)` takes the work
   registry as its first argument. Both the explicit `--work-child <id>` path
   and the producer-based auto path (config/graph.json `producerOf`) run
   against the work run's children.
2. **Fail-closed, naming which of the three**:
   - missing run → `missing run <X> — no registry at <path>` (checked at
     entry, before any resolution, via `existsSync(registryPath(X))`;
     `readRegistry` alone would return an EMPTY registry for a missing file
     and mask the miss as "no children");
   - missing child → `missing child "<Y>" in run "<X>"`;
   - different task → `child "<Y>" in run "<X>" has task <Z> but the verdict
     is for task <W>`. This check runs only on the `--work-run` path — the
     id-named child was found by id alone, so a same-id-different-task child
     would otherwise fingerprint an unrelated tree silently. Without the flag
     the old behaviour stands (spec point 3).
3. **Without the flag, behaviour is unchanged** — `workRunId` is null, the
   single-registry binding stays, and the record carries no `workRun` key
   (byte-identical shape). The existing 44 tests pass without change; the new
   "without --work-run" test pins `!("workRun" in record)`.
4. **Provenance** — the verdict record carries `workRun: <runId>` (only when
   the flag was given). When the record path touches a registry entry (the
   `pendingRuntimeReturn` stamp a fail writes onto the work child),
   `updateChild` now writes to the WORK CHILD's own run (`workChildRunId`) —
   pre-fix it wrote to the verdict's run, which cross-run silently created a
   stub entry in the wrong registry — and the patch carries `workRun` too.
5. **Cross-run fingerprint / roundsFor** — see below.

### Item 5 — cross-run fingerprint / roundsFor findings

`progressFingerprint` itself is UNAFFECTED by the run split: it hashes the
work child's tree (`worktree` + `baseRevision` come from the resolved child's
registry entry, which `--work-run` now fetches from the right run) plus the
declared failing tests. The blind spot was in the CHAIN VIEW:

- `roundsFor(runId, taskId)` (pre-fix `scripts/supervisor-lib.mjs:3024-3040`)
  read exactly one verdicts dir. After a restart, the pre-restart rounds sit
  in the old run's dir and the post-restart rounds in the new run's — so
  `supervisor-followup`'s FOC-1146 progress guard
  (`scripts/supervisor-followup.mjs:176`, `roundsFor(runId, entry.taskId)`)
  saw only the new run's rounds, and `last`/`prev` compared two rounds that
  were never adjacent in the task's real history. A round repeated across the
  split — the exact shape the guard exists to refuse — was invisible, and
  round numbering in `cmdRecord` (`latestVerdict(runId, ...)`) restarted at 1.
- **Fixed (small, in place)**: lib `roundsFor` now follows `workRun`
  provenance transitively (each run read once, records keyed by
  `<runId>/<file>` so no double count). Records written after the restart
  carry the work child's run as `workRun`; following that pointer rebuilds the
  chain across the split. Without provenance nothing is followed — single-run
  behaviour identical. Callers get this for free: `supervisor-followup` (the
  guard), `partialStatusReport`, `work-board` — the FOC-1146 guard semantics
  (refuse only on same verdict AND same findings,
  `supervisor-followup.mjs:248-275`) are untouched; the change is entirely in
  what the chain view returns.
- `cmdRecord`'s round numbering reads the merged chain explicitly
  (`taskRounds(runId, workRunId, taskId)`) because the FIRST cross-run record
  has not been written yet when the chain is read — its provenance cannot
  point back yet, so the work run is consulted directly; records seen in both
  chains dedupe on round+recordedAt.

**Residual blind spot (reported, not fixed — needs a redesign, follow-up
ticket):** the chain is discoverable ONLY through `workRun` provenance on
records. A verdict recorded in the new run WITHOUT `--work-run` (e.g. the
reviewer child already lives in the new run and the operator omits the flag)
carries no provenance, and the old run's rounds stay invisible to the guard.
Closing that without a second source of truth would need either (a) a
task-level chain pointer written at spawn/transition time, or (b) scanning
run dirs by taskId — both are supervisor-lib redesigns, not a small fix.
Also noted: `maybeEmitReturnGate` names `--child <workChild>` on a gate
emitted in the verdict's own run — cross-run the gate's childId does not
resolve in that run's registry; the gate record stores it as metadata only,
but a Supervisor answering the gate must resolve the child against the
`workRun` registry. Left as-is (gate plumbing is out of scope here);
follow-up ticket material.

## 2026-11-02 — round 2: the loop reads the chain from the WORK run (the reverse bridge)

### The gap (operator review of `4f22358`)

The round-1 journal overclaimed: "the FOC-1146 guard now sees the chain across
a split". Confirmed in source — on the real path it did not:

- `supervisor-followup.mjs --review-loop` resolves `--child` in **`runId`'s
  registry** (pre-fix `scripts/supervisor-followup.mjs:56-60, 176`). dev-1
  lives in run A, so the Supervisor resumes the loop with `--run A` — the
  only run the child can be resumed from.
- Round 1's provenance pointed only **B → A** (the record in B carries
  `workRun: A`); A's records carry nothing back to B. `roundsFor(A, task)`
  read A's verdicts dir alone, so a TEST fail recorded in run B was
  **invisible from A**.
- Result: the loop handed back stale findings or was refused with
  `no REVIEW verdict recorded for FOC-123 — there is nothing to send back to
  DEV` — exactly the case this ticket exists for. The round-1 tests walked
  the chain from B, a shape `--review-loop` never uses for a DEV child
  living in A.

### What round 2 changed (items 1–4)

1. **Reverse link stamped.** Every cross-run record (`--work-run A`, pass
   **and** fail alike) stamps the work child's entry in A with
   `verdictRuns: [B]` (deduplicated through `updateChild`; stamped before the
   record write, because a bridge without a record is a harmless no-op while
   a record without a bridge is a blind loop; a failed stamp refuses the
   record — fail closed). `scripts/supervisor-verdict.mjs`, `cmdRecord`.
2. **`--review-loop` reads the full chain.** The guard reads the entry's own
   run plus `entry.verdictRuns` and merges through the new lib
   `roundsAcross([runId, ...verdictRuns], taskId)` — each run read through
   `roundsFor`, which also follows `workRun` provenance; overlapping chains
   dedupe on round+recordedAt (a record exists in exactly one dir).
   `scripts/supervisor-followup.mjs` guard block; the FOC-1146 refusal
   semantics (same verdict AND same findings) are untouched — the change is
   only what the chain view returns. No directory scan; the provenance on the
   entry is the single source.
3. **Run-id shape validation.** `isPathSafeRunId` in `supervisor-lib.mjs`
   (permissive `[A-Za-z0-9._-]+` minus `.`/`..` — the shape
   `agent-records.mjs` and `fenix-retention.mjs` already use, because legacy
   `test-*`/`run-*` ids are legal dir names and the strict `RUN_ID_RE`
   launcher shape would reject the fixtures). Used at all three sites:
   the `--work-run` write path (refused by shape, naming the value —
   `<runB>/../<runB>` normalizes to an existing registry and read fine
   before), `workRun` read from disk in `roundsFor` (invalid provenance is
   never followed — it would become a path), and `verdictRuns` read from disk
   in `--review-loop` (refused with the value named; a non-array provenance
   is refused too).
4. **Round-1 helper consolidated.** The verdict tool's `taskRounds` is gone;
   round numbering reads `roundsAcross([runId, workRunId])` — same merge, one
   implementation shared with the loop.

### Named limitation (NOT fixed — the known blind spot)

**A verdict recorded in run B without `--work-run` creates no bridge at all**
— no `workRun` on the record, no `verdictRuns` on any entry. From run A the
loop then sees nothing: same stale findings or bogus refusal as before this
ticket. The Supervisor MUST pass `--work-run` on every cross-run record;
omitting it silently re-opens the gap. This is a limitation by design (the
provenance on the record/entry is the single source of truth — there is no
directory scan to fall back on), and it is named here as such, not claimed as
fixed.
