### 2. `cost-quality.mjs` — three signals + rename

- `DEFINITIONS.firstTimeRight` renamed to "Review first-time-right: share of tickets whose
  round-1 review verdict is PASS…". The VALUE is untouched — same `round1VerdictOf` filter,
  except one deliberate change: rows with `squad === "delivery"` no longer count as the round-1
  verdict. Without it, a delivery verdict recorded at round 1 (no review happened) would flip
  the review signal — pinned by "the old firstTimeRight is unchanged by delivery verdicts in the
  chain". `squad: null` rows (legacy, pre-squad) still count as review.
- `deliveryFirstTimeRight` — tickets whose first (by recordedAt) delivery verdict is PASS, among
  tickets with any delivery verdict.
- `reviewFalsePass` — REVIEW PASS rounds (squad exactly `review`; `null` is UNKNOWN, not assumed)
  followed by a delivery FAIL on the SAME non-null fingerprint, among REVIEW PASS rounds that
  have a later delivery verdict. Counted in ROUNDS, not tickets (that is the unit a pass is
  falsified in); the definition text says so.
- `ciRedAfterReady` — tickets with a delivery FAIL citing `reason: "ci"`, among tickets with any
  delivery verdict.
- All three in the same signal shape, `null` value at denominator 0, evidence capped at 20 like
  the old ones. Rows are ordered by `recordedAt` inside the signal computation (facts concatenate
  verdicts across runs; round numbers restart per run, timestamps do not).
- `work-board.mjs` verdict rows now carry `squad`, `fingerprint` (the record's
  `fingerprint.combined`), and `reason` — pass-through from the record, `null` when the record
  predates the field or is unreadable. Pinned by the new work-board test.

## 2026-11-02 — ambiguity calls the AC left open (and what was chosen)

- **Does a delivery pass need an AC mapping?** No — the spec's CLI signature has no `--ac`; the
  delivery verdict judges the delivered tree, not the issue's criteria list. `--ac` passed with
  `--delivery` is refused; `declaredAcs: null` on the record (UNKNOWN, never a count).
- **Does a delivery fail declare its failing-test axis?** Yes — same gate as a review fail
  (either `--failing-test` or `--no-failing-tests "<why>"`), because both records share the
  fingerprint that the FOC-1146 guard compares on the test axis.
- **What counts as a "REVIEW pass round" for `reviewFalsePass`?** Only rows with
  `squad === "review"`. `squad: null` (legacy pre-squad records) is UNKNOWN and is NOT assumed to
  be review — the same policy the rows already apply to unreadable files.
- **`--child` together with `--delivery`** → refused, not ignored: the record's `childId` is
  null by definition, and a child in the invocation would be a different record pretending to be
  this one.
- **Ordering of a task's verdict rows for the signals**: by `recordedAt`, not by round — round
  numbers restart per run dir while timestamps do not, and the backfill path exists precisely to
  write historical timestamps.

### Semantics decision (forced by the finding, recorded here)

The plan's "on the same fingerprint" CANNOT mean the fingerprint's `combined` hash:
`progressFingerprint` (`scripts/supervisor-lib.mjs:3017`) computes
`combined = sha(diffHash:testsHash)`, folding the DECLARED failing-test axis into work identity.
A REVIEW pass carries `failingTests: []`; a delivery FAIL must declare either `--failing-test`
(FOC-220 gate) or `--no-failing-tests <reason>` — so on combined, a test-backed delivery fail can
NEVER equal the pass it falsifies, and the signal's motivating case (CI red after READY, with the
failing test declared — the exact recipe `docs/supervisor-e2e-checklist.md` recommends) was
uncountable by construction. Inversely, a `--no-failing-tests` delivery fail WOULD match — the
code was blind precisely on the test-backed fails.

Decision: "same fingerprint" = **same work tree, the fingerprint's `diff` axis**. The tests axis
is a per-verdict declaration (FOC-220), not part of work identity; it exists for the FOC-1146
rework comparison (`comparableProgress` on `combined`), which is UNCHANGED. Null on either side
never matches (UNKNOWN is not evidence of a false pass).
