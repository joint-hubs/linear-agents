## 2026-11-02 — ambiguity calls the AC left open (and what was chosen)

- **Does a delivery pass need an AC mapping?** No — the spec's CLI signature has no `--ac`; the
  delivery verdict judges the delivered tree, not the issue's criteria list. `--ac` passed with
  `--delivery` is refused; `declaredAcs: null` on the record (UNKNOWN, never a count).
- **Does a delivery fail declare its failing-test axis?** Yes — same gate as a review fail
  (either `--failing-test` or `--no-failing-tests "<why>"`), because both records share the
  fingerprint that the FOC-1146 guard compares on the test axis.
- **What counts as a "REVIEW pass round" for `reviewFalsePass`?** Only rows with
  `squad === "review"`. `squad: null` (legacy pre-squad records) is UNKNOWN and is NOT assumed to
  be review — the same policy the rows already apply to unreadable files.
- **`--child` together with `--delivery`** → refused, not ignored: the record's `childId` is
  null by definition, and a child in the invocation would be a different record pretending to be
  this one.
- **Ordering of a task's verdict rows for the signals**: by `recordedAt`, not by round — round
  numbers restart per run dir while timestamps do not, and the backfill path exists precisely to
  write historical timestamps.

### Semantics decision (forced by the finding, recorded here)

The plan's "on the same fingerprint" CANNOT mean the fingerprint's `combined` hash:
`progressFingerprint` (`scripts/supervisor-lib.mjs:3017`) computes
`combined = sha(diffHash:testsHash)`, folding the DECLARED failing-test axis into work identity.
A REVIEW pass carries `failingTests: []`; a delivery FAIL must declare either `--failing-test`
(FOC-220 gate) or `--no-failing-tests <reason>` — so on combined, a test-backed delivery fail can
NEVER equal the pass it falsifies, and the signal's motivating case (CI red after READY, with the
failing test declared — the exact recipe `docs/supervisor-e2e-checklist.md` recommends) was
uncountable by construction. Inversely, a `--no-failing-tests` delivery fail WOULD match — the
code was blind precisely on the test-backed fails.

Decision: "same fingerprint" = **same work tree, the fingerprint's `diff` axis**. The tests axis
is a per-verdict declaration (FOC-220), not part of work identity; it exists for the FOC-1146
rework comparison (`comparableProgress` on `combined`), which is UNCHANGED. Null on either side
never matches (UNKNOWN is not evidence of a false pass).

### Blocking — calendar-overflow re-dating

`Date.parse("2026-02-30T00:00:00Z")` is `2026-03-02T00:00:00.000Z` — the old gate (regex +
NaN check) cleared it and the record stored a WHEN the operator never typed. Verdict rows
order by `recordedAt` and the delivery signals run on that order, so a shifted stamp could
silently reorder signal inputs. Fix (`scripts/supervisor-verdict.mjs`, the backfill block):

- `RE_ISO_STAMP` now CAPTURES the typed Y/M/D; after the shape + `Date.parse` checks, the
  typed date components are round-tripped against the calendar directly
  (`Date.UTC(y, mo-1, d)` must read back as the same y/m/d). 2026-02-30, 2026-02-29
  (non-leap), 2026-04-31 refuse; month 13 keeps refusing via NaN.
- The calendar check is offset-INDEPENDENT by design: the date is validated as typed, not as
  the parsed UTC datetime. (Round-3 wording fix — this paragraph originally used
  `2026-11-01T23:30:00+14:00` → `09:30Z` as its example, but that stamp keeps the SAME UTC
  date, so a parsed-UTC-parts comparison would NOT have refused it and the example overstated
  the argument. The real case is a typed local time earlier than the offset magnitude:
  `2026-11-01T09:30:00+14:00` records `2026-10-31T19:30:00.000Z` — a UTC date the typed date
  is not. Comparing against the parsed UTC parts would refuse exactly that.)
- Refusal names the typed date: `--recorded-at "2026-02-30T00:00:00Z" is not a real calendar
  date (2026-02-30 does not exist)`. The record keeps storing the parsed instant.

### Offset bound (round-2 nit 1, same pass)

The offset branch of `RE_ISO_STAMP` was `[+-]\d{2}:\d{2}` — it read `+99:99`. Bounded to
**±14:00, per ISO 8601** (decision recorded): the offset branch is now
`[+-](?:0\d|1[0-4]):[0-5]\d`. 23:59 was considered (ISO's own max magnitude is 14:00) — an
offset wider than the standard's is not a timezone anyone has.

Note on red-first for the offset pin: `+99:99` was ALREADY refused pre-fix — `Date.parse`
returns NaN for it, so the existing NaN gate caught it (the reviewer's finding was about the
REGEX accepting the shape, defense in depth, not about acceptance end-to-end). The pin stays;
the named pre-fix failure is the calendar one below.

### Blocking — the offset bound was ±14:59

`(?:0\d|1[0-4]):[0-5]\d` admits `+14:01`..`+14:59`, and `Date.parse` does not NaN them, so
the gate accepted them end-to-end (reviewer probe: `+14:01` recorded `2026-10-31T19:59:00.000Z`)

±14:00. Fix: hour 14 admits ONLY `:00` — the offset branch is now
`[+-](?:(?:0\d|1[0-3]):[0-5]\d|14:00)`. Probes: `+14:00` true, `+14:01`/`+14:59`/`+99:99`/
`+14:60` false.

Pins that can actually go red (the round-2 test could not — `+99:99` was refused pre-fix via
the NaN gate, and `+14:00` was accepted pre-fix too, so no case in it could fail at the
boundary): `+14:01` refused, `+14:59` refused, `+14:00` accepted. The red-first naming:
`a --recorded-at offset is bounded to ISO 8601 (±14:00 exactly), a real offset still records`
FAILED pre-fix (`59 passed, 1 FAILED`) on `+14:01` being accepted. (One test-harness fix along

the message with `includes` now. Test-side only, no tool change.)

### Nit 1 folded in — years 0000–0099 false refusal

Reviewer pre-cleared, and the gate was touched again this round, so the fix landed: the
round-trip anchored on `Date.UTC(y, mo-1, d)`, and Date.UTC maps years 0-99 onto 1900-1999

"does not exist" reason. Decision: `setUTCFullYear(y)` after anchoring on year 2000 (leap, so
Feb-29 anchors exist) — the round-trip now holds for EVERY year the shape allows, and
"not a real calendar date" stays a refusal that means exactly that. Probes: `0026-02-01`
accepted, `0026-02-30` refused, `0050-02-29` (non-leap) refused, `9999-02-28` accepted. A
backfill baseline stamped in the year 0026 is still nonsense, but it is now nonsense the
operator typed, not the validator's mapping artifact.

SAME UTC date; the real case is `09:30:00+14:00` → UTC date `2026-10-31`, which a
