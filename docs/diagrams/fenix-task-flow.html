How a task moves through Fenix

Five views of the same system: a boundary map (what the LLM does, what scripts do, what the outside world does), three sequences from hand-off to closing a task, and the telemetry data path. Each view stays within a readability budget, which is why the whole is split into several diagrams.

1 · Map: where the LLM meets the world2 · Task → triage → child spawn3 · Monitoring and gates (HITL)4 · Review loop → merge → close5 · Telemetry: where the numbers come from

1 · Map: where the LLM meets the world

  • Two LLM sessions: SUPERVISOR (talks to you) and SQUAD CHILD (codes in a worktree). Both act on the world only through Bash → Node scripts.
  • Three kinds of step from your sketch: reasoning = the LLM session itself (no arrow outward), tool call = the blue BASH arrow, script execution = the orange block and its arrows to Linear, Git and the child.
  • Linear is not reachable through MCP (mcp__linear__* is denied), only through linear-query/linear-ops. Linear writes and decision-seam calls pass an egress screen.

2 · Task → triage → child spawn

  • Propose is plain code (routing over the edges of config/graph.json). Only then does the LLM judge the verdict and confidence (record refuses confidence below 70 for any verdict but ask).
  • Spawn refuses without a recorded verdict. The child starts in a new worktree, in an isolated CLAUDE_CONFIG_DIR agents/<squad>, as headless claude -p owned by the watcher.
  • The optional intake (decision seam to OpenRouter) is in the contract but, per STATE.md, currently not invoked.

3 · Monitoring and gates (HITL)

  • The watcher owns the claude process and is the single writer of the event queue; the supervisor only drains and acknowledges it.
  • A gate is a file: the child ends its turn cleanly with an open question, the supervisor asks you and records the answer first, and only then resumes the child's session.
  • Stall = 10 minutes of silence in the tee. Then stop, report the dirty tree and ask you; never an automatic retry.

4 · Review loop → merge → close

  • Every REVIEW finding cites an artefact and an approve maps the ACs. Recording a fail verdict itself moves the issue to In Progress with the returned-by:review flag.
  • Merge is a separate verification: candidate alone, then the integration, same test command. The supervisor lands locally (merge --no-ff), no push.
  • Worktree cleanup needs two keys: TEST pass and your “yes” on the cleanup-approval gate.

5 · Telemetry: where the numbers come from

  • The SessionStart hook binds LA_RUN_ID to session_id, so transcript tokens land in the right run (children have their own runs).
  • Cost is computed with our own price list from config/models.json and cross-checked against the OpenRouter bill (flagged at more than 10% drift).
  • Summing usage_facts across the fleet overstates the result (run-scoped duplication), so fleet-wide questions go through canonical_usage.
